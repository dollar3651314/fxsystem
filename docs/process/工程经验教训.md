## L1. Spring bean 装配改动必须验 context 启动（2026-06-02，gateway C3 事故）

- **事故**：`GatewayWebSocketProxyMetrics` 有两个构造器且均无 `@Autowired`，本地 `mvn test` 全过（单测直接 `new`），部署后 gateway crash-loop（RestartCount=11）、app login 502。
- **根因**：Spring 多构造器无法选择且无 `@Autowired` 标注 → 回退找无参构造器失败。单测不经过 DI 装配，暴露不了。
- **规则**：新增 `@Component`/改构造器/改 bean 装配后，`mvn test` 通过**不等于**能启动；交付前必须有 context 启动证据——本地起 jar 验 `Started XxxApplication`，或跑一个会拉起完整 `@SpringBootTest`（Application class）的 IT。多构造器必须显式 `@Autowired` 标注选用构造器。

## L2. IT 手工注入上游数据会掩盖真实管线缺口（2026-06-03，demo FX USDT 事故）

- **事故**：STAGE-14B IT 用 `fxRateService.acceptUpdate("AUD","USDT",...)` 手工注入 USDT 汇率，测试全绿；demo 上真实 FX 管线只产 8 法币 USD 交叉对、根本没有 USDT 对 → 所有 quote→USDT 换算失败，开仓全拒 `FX_RATE_UNAVAILABLE`。
- **根因**：IT 注入的是"假设上游会有的数据"，掩盖了上游真实不产该数据的事实。
- **规则**：账户币/汇率/行情这类**必经维度**，IT 必须用真实数据源口径构造（走真实 seed/真实管线产出的形态），手工注入仅限测下游分支逻辑；上线前必须在真实环境对该维度做一次端到端复测。

## L3. 前端显示类修复必须验证渲染层数据，公式核验+粗看截图会误报（2026-06-03，K 线平移两次误报）

- **事故**：K 线组加点平移修复连续两次向用户误报"完成"——①只验了匿名 401 + 容器 running（僵尸容器没发现）；②只核了公式（base+offset≈mid）+ 粗看截图（下跌行情里 MID 线恰落在蜡烛区间，巧合当贴合），实际 `messageToQuote` 丢弃 `baseMid` 致 offset 恒 0，蜡烛从未平移。
- **根因**：公式核验证明"代码生效的话应该等于什么"，不证明"浏览器实际渲染了什么"；数据管线中途丢字段恰恰只有渲染层能暴露；浏览器还会缓存旧 index.html（旧 chunk 仍能加载成功）。
- **规则**：
  1. 显示类修复 → 读渲染组件的**真实数据**逐字段比对期望（如 lightweight-charts hover legend 的渲染 OHLC vs 后端数据+变换），≥3 个样本；
  2. 部署后核对页面 `<script src>` hash 与容器内 dist 一致，验证 URL 带 cache-bust（`?v=xxx`）；
  3. 写"A 字段驱动 B 显示"的功能前，先 grep 数据流每一跳（WS payload → store 映射 → 组件 props）确认字段不被中途丢弃（本案：`marketSocket.messageToQuote` 自 STAGE-12 起静默丢弃 `baseBid/baseAsk/baseMid/hasMarkup`）。

## L4. 风控参数表的"数学可行"≠"经济可行"（2026-06-03，tier 满杠杆瞬时强平）

- **事故**：tier 模板 T5-T10 每档 mmRate=1/maxLev，满足 DB CHECK（lev×mm≤1.0），但满杠杆开仓时 MM 占满 IM、强平缓冲≈0 → 按对手价成交后点差即触发强平（AUDCAD 300x 开仓 199ms 被强平）。
- **根因**：约束只防了"数学违规"（缓冲为负），没防"经济不可用"（缓冲小于点差）。T1-T4（crypto）按 lev×mm=0.5 设计，T5-T10 误写成 1.0，无人对照。
- **规则**：杠杆/保证金/费率类参数表设计时必须做**最坏路径试算**（满杠杆 + 点差 + 手续费下的存活性），并将设计准则显式写入 master 设计稿与 seed 生成器注释（本案：`maxLev×mmRate ≤ 0.5`，见 master §5.1 修正记录与 `tools/tier-seed/generate_tier_seed.py`）；同族模板逐一对照准则核查，不允许"其余行照抄旧值"。

## L5. 本地前端调试产物必须同步回主仓（2026-05，worktree 镜像漂移）

- **事故**：在 worktree 改前端文件调试通过，主仓未同步，Vite/Spring 实际 serve 的还是旧版，"修好的" bug 复现。
- **规则**：worktree 内调试通过的前端改动必须 cp/commit 回主仓后再验收；验收一律以主仓 serve 的版本为准。

## L6. 每次 boot 重跑的初始化脚本必须真幂等且零重负载（2026-06-03，market 假活 P0）

- **事故**：market 的 ClickHouse 初始化机制每次 boot 重跑全部 `CH_V*.sql`（无版本表）。CH_V2 给 kline `MODIFY TTL` 自带注释称"metadata-only"，实际 ClickHouse 默认 `materialize_ttl_after_modify=1` → 每次启动对全表发起 TTL 物化 mutation（且 CH_V3 随后又 REMOVE——每 boot 白跑一轮 add+materialize+remove）。kline 增长后 mutation 撞 ClickHouse 内存上限 → `Application run failed` → context 关闭但 JVM 存活 → **容器 running/RestartCount=0 的假活**，gateway 熔断 504。同日两次"market 僵尸"均为此因（曾误归因 `compose restart` 竞态——日志里 `run failed` 的堆栈才是实锤，验尸要看全日志不要看到第一个可疑点就停）。
- **规则**：
  1. 无版本守卫、每次启动重跑的初始化脚本，每条语句必须**真幂等且 O(1) 轻量**——"metadata-only"之类的断言要查官方文档确认默认行为（如 `materialize_ttl_after_modify`），不能凭注释自证；
  2. 启动后置任务（ApplicationRunner）失败会让 context 关闭而 JVM 不退出——排障时容器 `running` 不可信，先 `grep -E "run failed|GracefulShutdown"`；
  3. 修复：CH_V2 去 kline TTL + quote_tick 显式 `materialize_ttl_after_modify=0`；CH_V3 改「先 metadata-only 置 TTL 再 REMOVE」兼容有/无 TTL 两态（commit `6ac99f43`）。

## L7. demo 管理端 API 受 IP 白名单限制，登录后页面 QA 走本地等价验证（2026-06-04）

- **约束**：demo 管理端（`admin-falconx.lifebyteapp.dev`）静态站 `GET /` 返回 200，但 `/admin/*` API 受「内部系统 IP 白名单」限制——`scripts/deploy-to-server.sh` 烟雾测试能过是因为它从服务器本机（已白名单）跑；**本地 WSL 浏览器出口 IP 不在白名单**，登录 POST 报 `Failed to fetch`（edge 层直接拦，不是 90005 JSON），无法在 demo 上做登录后管理页的渲染层 QA。这是环境约束（设计如此），别误判为代码缺口。
- **本地等价验证（唯一可行的认证页渲染证据来源）**：① 临时把 `falconx-console-frontend/vite.config.ts` 的 `/admin`+`/ws` proxy target 指向 demo 后端（`https://app-falconx.lifebyteapp.dev` / `wss://...`，`secure:false`），dev server 起在 localhost（浏览器走 localhost 无 CF ECH / 无 IP 拦）、Node 代理转发到 demo（类似 curl，不受 ECH 影响）；验收后**务必还原 vite.config.ts**（勿提交临时改动）。② 或无后端时用浏览器 `window.fetch` 拦截伪造会话（sessionStorage 写 `falconx_admin_access_token`/`falconx_admin_user`，拦截 `/admin/auth/login`、`/admin/me/permissions`、`/admin/me/menus`、业务 list 端点，信封 `{code:"0",data}`），走真实登录表单触发 `loginSuccess` 填 zustand store。
- **补充**：客户端 demo（`app-falconx`）API **不受 IP 白名单**，可用真实账号（如 syy@1.com）经本地 proxy→demo 后端做带真行情的渲染层验收。Playwright 直连 demo 域名偶发 `ERR_ECH_FALLBACK_CERTIFICATE_INVALID`（Chromium ECH 与 CF 证书的瞬态问题，`curl`/Node 不受影响）→ 走 localhost dev proxy 规避。

## L8. Playwright addInitScript 是 context 级持久，多轮注入会叠层重复计数（2026-06-04）

- **坑**：用 `page.addInitScript` 注入探针（包装 `window.WebSocket`/`fetch` 计数）做多轮量测时，每轮脚本全部持久在 browser context 上、按注入顺序层层包裹 → 一次真实事件被每层各记一次，结果是真实数的整数倍（曾误报 WS「4 连接/双活」，干净 context 终验实为「2 连接/单活」，差点误开工单）。
- **规则**：跨轮 addInitScript 量测前必须重建 context（MCP playwright：`browser_close` 后再导航即新 context），或探针自带幂等守卫（`if (window.__probeInstalled) return; window.__probeInstalled = true`）。任何「计数翻倍/翻三倍」的探针结果先排除叠层再下结论。
