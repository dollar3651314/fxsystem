# FalconX 统一问题清单

## 1. 目的

本文件用于统一收敛 FalconX 当前仍需关注的活跃问题、审计项、补充整改项和待修复事项。

后续若需要“读取问题并修复”，默认先读本文件。若需要追溯已完成或不成立的问题，再读 [已归档问题清单](./archive/统一问题清单-已归档.md)。

适用范围：

- 架构问题
- 文档不一致问题
- 数据库设计问题
- 接口契约问题
- 事件与幂等问题
- 代码实现问题
- 测试缺口问题

## 2. 使用规则

1. 新问题优先追加到本文件，不再分散到其他临时问题文档。
2. 每个问题都必须注明：
   - 优先级
   - 当前状态
   - 问题描述
   - 涉及范围
   - 期望修复方式
3. 修复时必须先判断问题是否真实存在，再更新状态。
4. 问题状态进入 `已完成` 或 `不成立` 后，应移入 [已归档问题清单](./archive/统一问题清单-已归档.md)，保留审计记录。
5. `待确认 / 待修复 / 修复中 / 后续阶段处理` 问题继续保留在本文件，作为默认执行入口。

## 3. 状态约定

### 3.1 本文件默认保留的活跃状态

- `待确认`：问题已提出，但尚未核对是否真实存在
- `待修复`：问题已确认存在，等待实施
- `修复中`：问题正在处理
- `后续阶段处理`：问题成立，但按计划留到后续阶段实现

### 3.2 归档状态

- `已完成`：问题已修复并验证通过
- `不成立`：问题经核对后不成立，不需要修复

## 4. 优先级约定

- `P0`：必须立即处理，不修会阻塞当前阶段
- `P1`：应尽快处理，会影响下一阶段或核心质量
- `P2`：优化项或完整性补齐项

## [FX-057] wallet-service EVM 主网确认推进被整块 receipt 扫描拖慢

- 优先级：`P1`
- 当前状态：`已修复`

### 问题描述

修复前，生产化准备包中使用 Alchemy Ethereum Mainnet HTTPS 真节点已取得 ETH 原生币入金发现、`CONFIRMING`、`wallet.deposit.detected` outbox 和回滚 `REVERSED` 证据，但外部真节点 `CONFIRMED` 推进证据未形成。

修复前，`Web3jChainDepositListener` 在 Ethereum Mainnet 扫块时会遍历整块交易，并为合约交易逐条拉取 receipt 来识别 ERC20 `Transfer`。主网高交易量区块下，该路径耗时过高，确认窗口轮询无法稳定在验收时间内闭合；这会影响真节点确认推进证据，也会放大 RPC 限流和超时风险。

### 涉及范围

- 文档：
  - `docs/process/archive/ProdReady生产化准备包-2026-04-29.md`
  - `docs/test/CFD全面测试用例规范.md`
- 模块：`falconx-wallet-service`
- 文件：
  - `falconx-wallet-service/src/main/java/com/falconx/wallet/listener/Web3jChainDepositListener.java`
  - `falconx-wallet-service/src/test/java/com/falconx/wallet/listener/Web3jChainDepositListenerTests.java`
  - `falconx-wallet-service/src/test/java/com/falconx/wallet/WalletExternalChainNodeAutomationIntegrationTests.java`

### 期望修复

- 保留 ETH 原生币直接转账识别。
- ERC20 入金识别必须改为面向平台地址和 `Transfer` topic 的 `eth_getLogs` 或等效索引查询，不得继续依赖整块逐交易 receipt 扫描作为主路径。
- 补齐外部真节点 `DETECTED -> CONFIRMING -> CONFIRMED` 自动化证据，且日志中的外部 RPC URL 必须脱敏。

### 核对结论

- 是否真实存在：`是`
- 结论说明：2026-04-29 生产化准备定位中，Alchemy HTTPS 真节点发现和撤回用例均通过，但确认推进用例在主网确认窗口轮询中耗时过高，当前只能归档 `CONFIRMING` 与 `REVERSED` 外部证据。

### 修复记录

- 修复内容：`Web3jChainDepositListener` 已移除 ERC20 主路径中的逐交易 receipt 扫描；ETH 原生币转账继续按区块交易命中平台地址后读取 receipt 校验状态；ERC20 `Transfer` 改为按扫描区间、`Transfer` topic 与平台地址 indexed `to` topic 执行 `eth_getLogs`，并按平台地址分批查询。同步补充单测覆盖“合约交易不再拉 receipt、通过日志查询发现 ERC20 入金”、ERC20 metadata 单条失败隔离、已确认 ERC20 log 消失后 reversal 和外部真节点确认推进。
- 验证结果：2026-04-29 串行执行通过：`mvn -pl falconx-wallet-service -am -Dsurefire.failIfNoSpecifiedTests=false -Dtest=Web3jChainDepositListenerTests,WalletExternalChainNodeAutomationIntegrationTests test`（11 tests，2 skipped）；`mvn -pl falconx-wallet-service -am test`（32 tests，3 skipped）；使用 Alchemy HTTPS 与 `/tmp/falconx-combined-truststore.p12` 执行 `WalletExternalChainNodeAutomationIntegrationTests#shouldTrackRealEthDepositAcrossCursorRescanAndPersistWalletTxId` 通过（1 test，约 38.57 秒，真实 ETH 入金从 `CONFIRMING` 推进到 `CONFIRMED` 并写出 `wallet.deposit.confirmed` outbox）；执行 `WalletExternalChainNodeAutomationIntegrationTests#shouldEmitReversalWhenConfirmedTransactionDisappearsFromRealRescanWindow` 通过（1 test，约 8.67 秒）。

## [FX-071] 管理端客户管理雪花 ID 在前端 JSON.parse 精度丢失（P1 阻断详情 / freeze / unfreeze / 调余额 4 个 UI 流程）

- 优先级：`P1`
- 当前状态：**已修复并 R7 二轮 QA 通过**（2026-05-09，commit `795ab3b`）
- 发现来源：R7 阶段 2.1 浏览器 QA（2026-05-09）

### 问题描述

后端 `AdminCustomerListResponse.Item.userId` / `AdminCustomerDetailResponse.userId` / `FreezeUnfreezeResponse.userId` / `BalanceAdjustResponse.userId` 全部声明为 Java `long`，Jackson 默认序列化为 JSON `number`。

但 BBook 项目所有用户 ID 都是雪花算法生成（数据库里实测最小 `38541495015444480`、典型 `46482114006355968`），均**远超** JavaScript `Number.MAX_SAFE_INTEGER = 9007199254740991 ≈ 9.0e15`。

浏览器 `JSON.parse` 把 `46482114006355968` 解析成 `46482114006355970`（精度丢失最后几位），前端再用此值拼接路径 `/admin/customers/${userId}` 调后端 → 后端找不到客户 → 返回 `404` 或 `90303`。

R7 浏览器实测：
- `/admin/customers/46482114006355968` 详情页：fetch 实际请求 `/admin/customers/46482114006355970`，后端返回 404，前端展示 "客户不存在"。
- 由此连带阻断：客户详情、冻结、解冻、调余额 共 4 个 UI 流程。

后端 curl 直接传字符串 ID 无问题（已在 R7 后端 8 个测试中验证过）。

### 涉及范围

后端 4 个响应 DTO 的 ID 字段：

- `falconx-console-service/src/main/java/com/falconx/console/api/AdminCustomerListResponse.java`（`Item.userId`）
- `falconx-console-service/src/main/java/com/falconx/console/api/AdminCustomerDetailResponse.java`（`userId`）
- `falconx-console-service/src/main/java/com/falconx/console/api/AdminCustomerFreezeResponse.java` / `AdminCustomerUnfreezeResponse.java`（如有）
- `falconx-console-service/src/main/java/com/falconx/console/api/AdminBalanceAdjustResponse.java`（`userId` + 任何雪花 ID 字段）

前端：

- `falconx-console-frontend/src/features/customer/types.ts`：`userId: number` 4 处全部应改 `string`
- `falconx-console-frontend/src/features/customer/customerApi.ts`：`detail / freeze / unfreeze / adjustBalance` 的 `userId: number` 改 `string`
- `falconx-console-frontend/src/features/customer/CustomerDetailPage.tsx`：line 51 `Number(userId)` 改为 `userId!`（直接传 path 字符串）

R2 / R6：

- `docs/api/管理端接口规范.md` §3：客户管理 5 接口的响应字段表中 `userId` 类型从 `Long` 修订为 `String`（标注"为兼容 JavaScript Number 安全整数限制，所有雪花 ID 在 JSON 中以 String 序列化"）
- `docs/test/STAGE-2-CUSTOMER-test-cases.md`：补一个 TC 验证 ID > 2^53 时前端不丢精度

### 期望修复

1. 后端 4 个 DTO 的雪花 ID 字段加 `@JsonSerialize(using = com.fasterxml.jackson.databind.ser.std.ToStringSerializer.class)`；或在 `JacksonConfig` 中全局注册 `Long` → `String` SerializerFactory（注意：会影响所有 long 字段，需评估其它服务是否兼容）。
2. 前端 4 处 `userId: number` 改 `string`，去掉 `Number(userId)` 调用。
3. 同步更新 [`管理端接口规范`](../api/管理端接口规范.md) §3 + [`STAGE-2-CUSTOMER 测试用例`](../test/STAGE-2-CUSTOMER-test-cases.md)。
4. R7 二轮浏览器 QA 重跑 detail / freeze / unfreeze / 调余额 4 个流程，截图归档。

### 核对结论

- 是否真实存在：`真实存在`
- 结论说明：R7 浏览器 console 实测 `/admin/customers/46482114006355968` 触发 404 且 path 在 fetch 时变为 `46482114006355970`，前端代码 `Number(userId)` 精度丢失证据成立；后端 curl 字符串 path 调用同接口能正常返回 200，进一步证明问题发生在前端 JSON 反序列化阶段，而非后端。
