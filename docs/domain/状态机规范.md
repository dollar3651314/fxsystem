# FalconX v1 状态机规范

## 1. 目标

统一一期关键业务对象的状态定义、允许迁移方向和 owner。

## 2. 用户状态

owner：

- `identity-service`

状态：

- `ACTIVE`
- `FROZEN`
- `BANNED`

历史兼容状态：

- `PENDING_DEPOSIT`：仅用于兼容历史数据，不作为用户可见账户不可用状态，不作为登录拦截状态；新注册用户不得进入该状态

允许迁移：

- `ACTIVE -> FROZEN`
- `FROZEN -> ACTIVE`
- `ACTIVE -> BANNED`
- `FROZEN -> BANNED`
- `PENDING_DEPOSIT -> ACTIVE`（仅允许历史数据归一化）

说明：

- `BANNED` 为终止态，一期不设计自动恢复
- 注册完成后用户状态直接为 `ACTIVE`，`t_user.activated_at` 记录账户可用时间
- 是否已入金由入金事实、账户资金状态或独立入金历史标记表达，不得通过用户账户可用状态表达
- 邮箱可信度由 `t_user.email_verified` 独立表达，不进入用户账户可用状态机；一期 `email_verified=0` 不限制登录、Refresh 或交易

**入金完成后的 identity 处理机制：**

`falconx.trading.deposit.credited` 的完整跨服务链路如下：

1. `wallet-service` 链上确认完成，发布 `falconx.wallet.deposit.confirmed`
2. `trading-core-service` 幂等消费，执行入账，写 `t_account / t_ledger / t_deposit`
3. `trading-core-service` 完成入账后，通过 Outbox 发布 `falconx.trading.deposit.credited`（payload 含 `userId`）
4. `identity-service` 消费 `falconx.trading.deposit.credited`，写入 `t_inbox` 完成幂等留痕；若历史用户仍为 `PENDING_DEPOSIT`，归一化为 `ACTIVE` 并补齐 `t_user.activated_at`

约束：

- `identity-service` 消费时必须做幂等（用 `eventId` 去重）
- 若用户状态已为 `ACTIVE`，直接幂等跳过，不报错
- `FROZEN` 或 `BANNED` 用户收到此事件，不触发状态迁移（幂等返回原状态）

## 3. 钱包入金原始交易状态

owner：

- `wallet-service`

状态：

- `DETECTED`
- `CONFIRMING`
- `CONFIRMED`
- `REVERSED`
- `IGNORED`

允许迁移：

- `DETECTED -> CONFIRMING`
- `CONFIRMING -> CONFIRMED`
- `CONFIRMED -> REVERSED`
- `DETECTED -> IGNORED`
- `CONFIRMING -> IGNORED`

说明：

- `REVERSED` 用于链回滚或业务撤销
- `IGNORED` 用于无效或不归属平台的交易
- 未确认阶段若观察到链上回滚或交易消失，不直接进入 `REVERSED`，而是按业务语义处理为保留原状态或 `IGNORED`
- `confirmedAt` 的语义固定为“首次达到最终确认阈值的时间”，后续确认数增长时不得覆盖原值

## 4. 业务入金状态

owner：

- `trading-core-service`

状态：

- `CREDITED`
- `REVERSED`

允许迁移：

- `CREDITED -> REVERSED`

说明：

- 一期业务入账事实表只保留最终结果，不保留复杂中间态

## 5. 订单状态

owner：

- `trading-core-service`

状态：

- `PENDING`
- `TRIGGERED`
- `FILLED`
- `CANCELLED`
- `REJECTED`

允许迁移：

- `PENDING -> FILLED`
- `PENDING -> REJECTED`
- `PENDING -> CANCELLED`
- `PENDING -> TRIGGERED`
- `TRIGGERED -> FILLED`
- `TRIGGERED -> REJECTED`
- `TRIGGERED -> CANCELLED`

说明：

- 一期市价单主链路通常直接 `PENDING -> FILLED/REJECTED`
- `TRIGGERED` 为后续限价单和止损单预留
- 非交易时段、节假日全休或人工例外停盘时，拒绝新的开仓请求；手动平仓、TP/SL 自动平仓和强平执行也不得使用休盘报价触发新的成交事实

## 6. 持仓状态

owner：

- `trading-core-service`

状态：

- `OPEN`
- `CLOSED`
- `LIQUIDATED`

允许迁移：

- `OPEN -> CLOSED`
- `OPEN -> LIQUIDATED`

说明：

- `CLOSED` 和 `LIQUIDATED` 都是终态
- `OPEN` 持仓允许发生"追加逐仓保证金"资金动作，但该动作不会触发状态迁移（对应 [逐仓模式改造方案](../process/逐仓模式改造方案.md) §5.2 D1 冻结）
- 手动平仓成功时写 `close_reason=1=manual`
- 手动平仓成功时同事务写本地 `t_outbox.event_type=trading.position.closed`
- `take_profit_price / stop_loss_price` 属于持仓级参数，允许在 `OPEN` 状态下修改
- 追加逐仓保证金成功时必须同步更新 `margin / liquidation_price`，并保持 `status=OPEN`；`liquidation_price` 的重算在写路径内与 `margin` 更新同事务完成
- 追加逐仓保证金当前不新增 Kafka 业务事件（对应 [逐仓模式改造方案](../process/逐仓模式改造方案.md) §5.2 D2 冻结）；审计事实以 `t_ledger.biz_type=10` 和持仓最新快照为准
- 非交易时段、节假日全休或人工例外停盘时，已存在持仓不得因休盘报价触发手动平仓、TP/SL 自动平仓或强平成交；系统只保留持仓状态，等待可成交报价恢复后再执行
- 多头触发条件：
  - `effective_mark_price >= take_profit_price` 触发止盈
  - `effective_mark_price <= stop_loss_price` 触发止损
- 空头触发条件反向：
  - `effective_mark_price <= take_profit_price` 触发止盈
  - `effective_mark_price >= stop_loss_price` 触发止损
- `effective_mark_price` 的当前统一口径为：`BUY / 多头 -> bid`，`SELL / 空头 -> ask`
- 由 TP/SL 关闭的持仓，`close_reason` 分别记录为 `2=tp`、`3=sl`
- 手动平仓、强平执行与追加逐仓保证金必须统一使用 `SELECT FOR UPDATE` 锁定持仓 owner 记录
- 强平执行前必须基于最新 DB 持仓二次校验 `margin / liquidation_price`；若补仓后已不满足强平条件，则取消本次强平执行

### 6.1 净持仓模型冻结说明（SPEC-TRD-001）

- 单用户单 `symbol` 任一时刻最多只允许存在一个 `OPEN` 净持仓
- 同向下单：当前净仓加仓
- 反向下单且数量小于当前净仓：当前净仓减仓
- 反向下单且数量等于当前净仓：当前净仓减为 `0` 并进入终态
- 反向下单且数量大于当前净仓：先把当前净仓减为 `0`，剩余数量翻为反向净仓
- 净持仓模型下保留“每用户每 `symbol` 一个稳定 `positionId`”
- 后续正式实现中，加仓、减仓、穿零翻仓都在同一稳定 `positionId` 上演进，不额外创建新的独立持仓主键
- 本节为产品规则冻结，不代表当前仓库状态机实现已切换完成

### 6.2 MarginLevel 阶段状态机（STAGE-14C1，master §6.2）

owner：

- `trading-core-service`（`MarginLevelMonitor` / `MarginLevelStatus`）

MarginLevel 是基于持仓权益与维持保证金计算的派生状态，不落 schema 列，由 `MarginLevelMonitor` 基于实时报价重算判定。三态：

| 状态 | 条件 | 行为 |
|------|------|------|
| `HEALTHY` | `MarginLevel > marginCallLevel`（默认 100%） | 无动作 |
| `MARGIN_CALL` | `stopOutLevel < MarginLevel ≤ marginCallLevel`（默认 30% < ML ≤ 100%） | 发 `MARGIN_CALL_TRIGGERED` 站内信 + 同用户 5min 节流；**不强平** |
| `STOP_OUT` | `MarginLevel ≤ stopOutLevel`（默认 30%） | 触发强平 + 发 `STOP_OUT_TRIGGERED`（见 §6.3） |

口径与边界：

- 阈值来源：`t_risk_config` 平台行（`symbol IS NULL`）的 `stop_out_level / margin_call_level`（小数，0.30 / 1.00），本地短 TTL 缓存（默认 30s），平台行缺失用默认 0.30 / 1.00 兜底
- 计算口径：`MarginLevel` 内部为百分比数值（×100，如 184.06），判定前换算为小数（`ratio = MarginLevel / 100`）再与阈值比较
- ISOLATED 单仓：`Equity_i = margin_i(AC) + uPnL_i(AC)`；`MM_i = notional_i(AC) × mmRateAtOpen`（MM 用开仓冻结 `mm_rate_at_open` + 冻结 fx；**实时 MM 即 master §3.2 D2 全实时精化留 STAGE-14D**）；`MarginLevel_i = Equity_i / MM_i × 100%`
- 账户级：`Equity = balance + frozen + ΣuPnL`；CROSS 路径延 STAGE-14D
- `MarginLevel == null`（FX 不可用 / 无持仓 / 除零等降级）→ 判定为 `HEALTHY`（不告警不强平），此时 `liqPrice` 仍独立生效
- 通知模板（V31 seed）：`MARGIN_CALL_TRIGGERED` / `STOP_OUT_TRIGGERED`，占位 `${marginLevel}`（百分比数值）/ `${symbol}`

### 6.3 ISOLATED StopOut 强平流程（STAGE-14C1，master §6.3）

owner：

- `trading-core-service`（`QuoteDrivenEngine` + `closePositionByTrigger`）

`QuoteDrivenEngine` 每 tick 对受影响用户重算单仓 MarginLevel，强平采用**双触发**，任一命中即按 `LIQUIDATION` 强平：

1. **liqPrice 价格触发**：`effective_mark_price` 命中 `liquidation_price`（既有路径，TP/SL/强平统一价格判定）
2. **MarginLevel 触发**：单仓 `MarginLevel ≤ stopOutLevel`（默认 30%）

双触发归一：

- 两条触发都走统一的 `closePositionByTrigger`，内部 `SELECT FOR UPDATE` 锁定持仓 owner 记录并基于最新 DB 二次校验，防重复强平（同一 tick 同一仓位只调一次）
- 仅 `MarginLevel` 触发（非纯 liqPrice）才补发 `STOP_OUT_TRIGGERED` 站内信并填真实 MarginLevel 数值；纯 liqPrice 触发不发，避免对纯价格强平误报保证金率
- 强平成功后失效该用户账户内存缓存（balance/frozen/marginUsed 已变）

ISOLATED 下 liqPrice 与 MarginLevel 的关系：

- ISOLATED 单仓的强平价 `liquidation_price` 与 `MarginLevel = 100%`（即 Equity = MM）在数学上等价，两条触发在 ISOLATED 下基本同时命中
- **MarginLevel 独立触发的价值体现在 CROSS / STAGE-14D**：账户级跨仓共担保证金时，单一 liqPrice 不再等价于账户强平条件，需以账户级 MarginLevel 作为强平判据（CROSS 路径延 STAGE-14D）

### 6.4 账户 margin mode 切换状态机（STAGE-14D1，master §6.1）

owner：

- `trading-core-service`（`MarginModeSwitchApplicationService` + `GET/POST /api/v1/me/margin-mode`）
- 状态载体 `t_account.margin_mode`（TINYINT，1=CROSS / 2=ISOLATED，V11）+ `mode_changed_at` + `mode_cooling_until`（V33，DATETIME(3) NULL）

用户在 ISOLATED ↔ CROSS 之间切换。切换在 `@Transactional` 内对账户行 `SELECT FOR UPDATE` 加锁后，按以下顺序判定**切换闸门 4 项 + D1 临时 CROSS gate**，任一命中即拒，全过则落库（`margin_mode + mode_changed_at=now + mode_cooling_until=now+5min`）：

| 序 | 闸门 | 拒绝码 |
|---|---|---|
| 1 | 目标模式 = 当前模式 | `30083` MODE_NO_CHANGE（同模式短路） |
| 2 | 目标 = CROSS 且 `cross_mode.enabled` 关闭 | `30088` CROSS_MODE_NOT_ENABLED（**D1 临时 gate**，默认 false，CROSS 强平/实时 MM 就位前不放行，D2 打开） |
| 3 | 存在 OPEN 持仓 | `30080` MODE_HAS_OPEN_POSITIONS |
| 4 | 存在开仓挂单 | `30081` MODE_HAS_ACTIVE_PENDING |
| 5 | 处于冷静期（`mode_cooling_until > now`） | `30082` MODE_COOLING_PERIOD_ACTIVE |

冷静期：

- 切换成功后写 `mode_cooling_until = now + coolingDuration`（默认 **5min**）。**STAGE-14D3a（V37）起冷静期改从 `t_risk_config` 平台行 `cooling_period_seconds` 直读（admin 运行时可配 **60-604800 秒**，缺失回退 properties `falconx.trading.margin-mode.cooling-duration` 默认 300s），由 `MarginModeSwitchApplicationService` 消费、无缓存即时生效；admin 写经 trading-core internal RPC `PUT /internal/v1/trading/console/config/cooling-period`（见 [统一接口文档 §3.32](../api/FalconX统一接口文档.md)）。console 配置 UI（透传 + RBAC）留 D3b。**
- 冷静期内重复切换被 30082 拒绝；**冷静期到期（`mode_cooling_until ≤ now` 或 NULL）后允许再次切换**（由 `isInCoolingPeriod` 判定）。
- 历史账户 `mode_cooling_until` 默认 NULL（未发生过切换），不在冷静期。

查询（`GET /api/v1/me/margin-mode`）返回 `canSwitch` + `blockers`（`OPEN_POSITIONS` / `ACTIVE_PENDING` / `COOLING` 子集）；CROSS gate 与目标模式相关，不属于账户固有状态，不进 blockers，由 POST 按目标模式判定 30088。

切换成功后在同一事务内：发 Outbox `falconx.trading.account.mode.changed`（见 [Kafka 事件规范](../event/Kafka事件规范.md)）+ ACCOUNT_MODE_CHANGED 站内信（V34 模板），与状态变更原子（rollback 一并回滚）。

> CROSS 账户级强平排序「浮亏最大优先」+ 实时 MM 精化 + 放开 C1 latent 耦合 `closePositionByTrigger` 二次价格校验 + FX_PAUSED 8×3 完整验收 + 升级窗口 `isolated_margin` 回填，均随 D2/D3 收口；D1 仅落用户级切换闸门 + 冷静期 + supplement，CROSS 入口由 30088 gated。

### 6.5 FX_PAUSED / GLOBAL_PAUSE 按品种类目行为（STAGE-14C2，master §6.5）

owner：

- `trading-core-service`（`DefaultTradingRiskService.evaluatePauseOpenRejection` 开仓侧 + `QuoteDrivenEngine.shouldSkipLiquidationDuringPause` 被动强平侧）
- 数据源 `t_fx_pause_behavior`（8 类目 PK + `allow_open` / `allow_close` / `allow_liquidation`，V31 seed，本地缓存 TTL/刷新/降级），品种类目来自 `SymbolSpec.category()`（market owner 写入 Redis 快照，STAGE-14C2 Task 1 起填充）

当存在活跃 `GLOBAL_PAUSE`（含 FX_PAUSED 升级而来）风控动作时，不再对开仓一刀切全拒，而是按下单品种类目查 `t_fx_pause_behavior` 细分判定：

| 路径 | 判据 | 命中行为 |
|---|---|---|
| 开仓 | `allow_open=false`（如 forex / metal 默认） | 拒单业务码 `30087`，拒单原因 `GLOBAL_PAUSE_ACTIVE` |
| 开仓 | `allow_open=true`（如 crypto） | 不因 pause 拒，继续走品种级别风控动作（REJECT_OPEN / REDUCE_ONLY / SUSPEND_SYMBOL） |
| 被动强平 | `allow_liquidation=false`（如 forex / metal 默认） | 跳过该 tick 的被动强平（`continue`，记 WARN `trading.liquidation.skip.fx-paused`） |
| 被动强平 | `allow_liquidation=true` | 强平照常执行 |
| supplement（追加逐仓保证金） | `allow_open=false` 或 category/behavior 缺失（STAGE-14D3a） | 拒单业务码 `30087` GLOBAL_PAUSE_ACTIVE（supplement 视同「开仓侧加保证金」，复用 `allow_open`） |
| supplement（追加逐仓保证金） | `allow_open=true` | 不因 pause 拒，继续后续校验（余额等） |
| 平仓 | master §6.5 `allow_close` 始终=1 | 用户手动平仓不经本路径，不加 pause 限制 |

> **STAGE-14D3a supplement 接闸门**（commit `7633a361`）：`TradingPositionMarginApplicationService.addIsolatedMargin` 在 `POSITION_NOT_ISOLATED`（30085）校验之后、余额（40001）之前接 FX_PAUSED 闸门，口径与开仓侧 `evaluatePauseOpenRejection` 一致（`allow_open` 开关；category=null 或 behavior 缺失保守全拒 30087）。supplement 端降级统一 30087（开仓侧降级码为 30009 `BBOOK_RISK_GLOBAL_PAUSE`），符合 master §7.4 supplement 错误集含 30087。
>
> **STAGE-14D3a 8 类目×3 开关组合完整验收（master §8.3 D 阶段硬约束）**：8 类目（crypto/forex/metal/index/energy/stock/etf/other）× 3 开关（`allow_open` 影响开仓 + supplement、`allow_close` 恒 1 手动平仓始终通、`allow_liquidation` 影响被动强平）行为矩阵由 `FxPauseBehavior8x3AcceptanceIntegrationTests` 22 IT 完整验收（含 admin override 翻转可配即时生效 + category=null 双向降级），见 [R7 报告 §4/§7](../test/STAGE-14D3a-CONFIG-BACKEND-R7-verification-report.md)。admin 写路径经 trading-core internal RPC（`PUT /internal/v1/trading/console/config/fx-pause-behavior/{category}`，写后失效快照即时生效，`allow_close` 写时恒 1）。

降级方向（缺信息时**两侧相反**，由各自风险性质决定）：

- **开仓从严**：`category==null`（过渡期旧 Redis 快照无 category）或 `t_fx_pause_behavior` 命中缺失 → 回退原一刀切全拒（`BBOOK_RISK_GLOBAL_PAUSE`）+ WARN。pause 期间宁可多拒一笔，也不放过高风险开仓。
- **被动强平从宽**：`category==null` 或 behavior 缺失 → 不跳过、继续强平（保持 C1 现状）+ WARN。强平是保护性动作，缺信息时倾向继续以防穿仓。

> 过渡期注意：market-service 重发布前旧 Redis `SymbolSpec` 快照无 `category` 字段（向后兼容反序列化为 null），此时开仓保守全拒 / 强平继续；market 重发布补齐 category 后行为按类目精确生效（同 STAGE-14B currency 过渡口径）。

### 6.6 CROSS 账户级强平流程（STAGE-14D2，master §6.3）

owner：

- `trading-core-service`（`CrossLiquidationOrchestrator` 账户级编排 + `QuoteDrivenEngine` CROSS 接入 + `closePositionByTrigger` 逐仓落账）

CROSS 账户（`cross_mode.enabled=true` 打开后）的强平判据**不再是单仓 liqPrice**（CROSS 仓 `liquidation_price=null`），而是**账户级 MarginLevel**。`QuoteDrivenEngine` 每 tick 对受影响 CROSS 用户调 `CrossLiquidationOrchestrator.evaluateAndLiquidate(userId, accountCurrency)`：

1. **Redisson user-level 锁** `cross-liq:{userId}` `tryLock(0,...)` 不等待——获取不到说明该用户正被另一 tick 评估，直接跳过本次（下个 tick 再来），不阻塞 tick 线程。锁只串行化「同一用户多 symbol tick 的账户级评估」，与单仓 `FOR UPDATE` 维度正交，不死锁。
2. 锁内取该用户全部 OPEN 持仓 + 读账户只读快照（`AccountMarginStateCache`，不与 close 服务的 `FOR UPDATE` 争锁），各仓组 `PositionMarkInput`（effectiveMark + quoteCurrency）。
3. `AccountEquityCalculator.computeAccountMarginLevel` 算**账户级 ML**（实时 MM，见 §6.3 补充）。
4. ML==null（FX 不可用降级 / 无持仓 / 除零）或 ML/100 > stopOut（默认 30%）→ 不强平返回。
5. ML/100 ≤ stopOut（**跌穿**）：按各仓 `|uPnL(账户币)|` **降序**排序（FX 不可用 / 无报价的仓 uPnL 视作 0 排末尾）→ **浮亏最大优先逐仓** `closePositionByTrigger(positionId, CROSS_STOP_OUT, quote)` → 平成功后失效账户缓存 + **重新取剩余 OPEN 持仓重算账户级 ML** → ML/100 > stopOut（**恢复**）即止步（避免过度强平）。无可成交报价的仓跳过不阻断其余仓。

落账与通知：

- 逐仓 close 走 `CROSS_STOP_OUT`（与 `LIQUIDATION` 同口径：LIQUIDATED 状态 + `t_ledger.biz_type=9` + `t_liquidation_log`，`liquidation_price=NULL`，见数据库设计 V35 / Kafka §12.16）。
- 逐仓 `POSITION_LIQUIDATED` 站内信**去重**：改由编排器在一轮强平结束后发**一条**账户级 `CROSS_STOP_OUT_TRIGGERED`（marginLevel=触发时账户 ML / count=强平仓数 / symbols=强平 symbol 清单，relatedKey=ACCOUNT，V36 模板）。

> CROSS 入口由 `cross_mode.enabled`（默认 **false**）gated；D2 代码全链就位（CROSS 开仓 + 账户级强平 + 实时 MM），生产启用由 admin 经 risk-switch 接口开启 `cross_mode.enabled`（运维决策）。

### 6.3 补充：实时 MM 精化（STAGE-14D2，master §3.2）

§6.3（ISOLATED）与 §6.6（CROSS）的 MarginLevel 重算均接**实时维护保证金（MM）**（master §3.2 D2「全部实时」）：

- `maintenanceMargin = Σ(notional_i × mmRate_i × 实时 fx_i)`：`notional` 用持仓本金、`mmRate` 用**开仓冻结** `mm_rate_at_open`（tier 冻结不随行情变），**fx 用实时汇率**（FX 变 → MM 变 → ML 变 → 触发判据随行情实时移动）。
- **FX 不可用降级**：实时 fx 取不到时该仓 MM 回退用**开仓冻结** `entry_fx_rate` 估算（不阻断 ML 计算，保持强平判据可用），并告警。
- ISOLATED 在 C1 因 IT seed fx 同值无数值漂移（回归绿）；D2 实时 MM 对 ISOLATED/CROSS 一致生效。

## 7. 行情时效状态

owner：

- `market-service`

运行态：

- `FRESH`
- `STALE`
- `NO_QUOTE`
- `MARKET_CLOSED`
- `ABNORMAL`

规则：

- `FRESH` 是唯一可成交状态。
- 若 `abs(now - quote.ts)` 超过 `falconx.market.stale.max-age`，market-service 将该 tick 标记为 `STALE`；trading-core-service 读取 Redis 快照时仍必须结合 `falconx.trading.stale.max-age` 做二次动态校验。
- 若同一 `symbol` 的 `bid / ask` 超过 `falconx.market.quote-quality.unchanged-max-age` 没有变化，market-service 将该 tick 标记为 `NO_QUOTE`，默认阈值为 `1m`。
- 若交易日历、周内交易时段或人工例外判定该 `symbol` 已休盘，market-service 将该 tick 标记为 `MARKET_CLOSED` 并跳过 Redis 最新价、ClickHouse、Kafka、WebSocket 和 K 线写入。
- 若 `bid <= 0`、`ask <= 0` 或 `bid >= ask`，market-service 将该 tick 标记为 `ABNORMAL`。
- `STALE / NO_QUOTE / MARKET_CLOSED / ABNORMAL` 均为不可成交状态，不允许进入下单、手动平仓、TP/SL 或强平触发。

业务影响：

- 开仓拒绝使用不可成交报价；无报价返回 `30003`，过期或异常报价返回 `30002`，休盘返回 `40008`。
- 手动平仓同样拒绝使用不可成交报价；无报价返回 `30003`，过期或异常报价返回 `30002`，休盘返回 `40008`。
- TP/SL 和强平只允许基于 `FRESH` 且交易时段打开的 tick 触发；不可成交 tick 只能更新参考快照或审计日志，不得写成交、账本、持仓终态或强平日志。

## 7A. 出金状态机（STAGE-7-WITHDRAW Phase 0 冻结）

owner：

- `trading-core-service`（驱动状态机；`t_withdraw_order.status`）

数值映射：

- `COOLING = 0` 用户提交后的 2h 冷静期
- `PENDING = 1` 冷静期结束，等待 admin 审核
- `APPROVED = 2` 小额（<$3000）审核通过，直接进入广播队列
- `APPROVED_DELAYED = 3` 大额（≥$3000）审核通过，额外 6h 延迟期内可紧急取消
- `PROCESSING = 4` wallet 已链上广播，等待确认
- `COMPLETED = 5` 链上达 min_confirmations 后终态
- `FAILED = 6` 链上失败终态（已回滚冻结余额）
- `CANCELED = 7` 用户冷静期取消 / admin 紧急取消（已回滚冻结余额）
- `REJECTED = 8` admin 拒绝（已回滚冻结余额）

允许迁移（按事件驱动方）：

```
[user 提交]
   ↓
COOLING ────[coolingUntil 到期 / 调度器]──→ PENDING
COOLING ────[user 取消]──────────────────→ CANCELED
PENDING ────[admin approve, amount<$3000]→ APPROVED
PENDING ────[admin approve, amount≥$3000]→ APPROVED_DELAYED
PENDING ────[admin reject]───────────────→ REJECTED
APPROVED_DELAYED ──[admin emergency cancel]→ CANCELED
APPROVED_DELAYED ──[delayedUntil 到期]────→ APPROVED
APPROVED ────[wallet 广播 tx 成功]────────→ PROCESSING
APPROVED ────[wallet 广播失败]────────────→ FAILED
PROCESSING ──[链上确认达 min_confirmations]→ COMPLETED
PROCESSING ──[链上 revert / 超时 / nonce 冲突]→ FAILED
```

禁止迁移：

- `COMPLETED / FAILED / CANCELED / REJECTED` 均为终态，不得回退
- `PROCESSING → PENDING / APPROVED` 禁止（已广播的 tx 不可逆，必须等链上结果）
- `APPROVED / APPROVED_DELAYED → PENDING` 禁止（审核结论一旦下达不可撤回，只能 emergency_cancel）

余额时点（trading-core 一致性）：

- 提交（→ COOLING）：`t_account.frozen += amount`；`t_ledger.biz_type=13 withdraw_freeze`
- 用户取消（COOLING → CANCELED）：`t_account.frozen -= amount`；`biz_type=14 withdraw_refund_cancel`
- admin 拒绝（PENDING → REJECTED）：`t_account.frozen -= amount`；`biz_type=15 withdraw_refund_reject`
- admin 紧急取消（APPROVED_DELAYED → CANCELED）：`t_account.frozen -= amount`；`biz_type=16 withdraw_refund_emergency`
- 链上确认（PROCESSING → COMPLETED）：`t_account.frozen -= amount` + `t_account.balance -= amount`；`biz_type=17 withdraw_settle`
- 链上失败（PROCESSING/APPROVED → FAILED）：`t_account.frozen -= amount`；`biz_type=18 withdraw_refund_chain_failed`

> ⚠️ STAGE-7-WITHDRAW Phase 1 修订（2026-05-14）：Phase 0 R2 蓝图把 withdraw biz_type 写到
> 12-17，但 trading-core 现有代码已经把 12 占给 `PENDING_ORDER_RELEASED`（STAGE-3-PENDING-ORDER），
> 因此 R4 实施时整体下移到 13-18，与 `TradingLedgerBizType` 枚举一致。本节、SQL 蓝图、REST §9.2
> 已同步。

CAS 写入：

- 所有 status 更新使用 `UPDATE ... WHERE id=? AND status=?`（旧态）保证幂等 + 并发安全
- 并发 admin approve / reject 由 trading-core 数据库行锁串行化

调度器：

- `WithdrawCoolingScheduler`：每 30s 扫描 `status=COOLING AND cooling_until <= now()` → 状态机 → PENDING
- `WithdrawDelayedScheduler`：每 60s 扫描 `status=APPROVED_DELAYED AND delayed_until <= now()` → 状态机 → APPROVED
- `WithdrawProcessingTimeoutScheduler`：每 5min 扫描 `status=PROCESSING AND processing_started_at + 30min <= now()` → 触发 wallet 端的失败回滚

事件发布（详见 [Kafka 事件规范 §12.8-12.12](../event/Kafka事件规范.md)）：

- `COOLING` 写入后 → Outbox `falconx.trading.withdraw.requested`（admin 待办通知 + 审计）
- `APPROVED / APPROVED_DELAYED / REJECTED` 写入后 → Outbox `falconx.trading.withdraw.reviewed`（wallet 异步广播）
- wallet 广播成功 → 发布 `falconx.wallet.withdraw.broadcast` → trading-core 切到 `PROCESSING`
- wallet 链上确认 → 发布 `falconx.wallet.withdraw.confirmed` → trading-core 切到 `COMPLETED`
- wallet 失败 → 发布 `falconx.wallet.withdraw.failed` → trading-core 切到 `FAILED`

## 7B. KmsSigner 抽象（STAGE-7-WITHDRAW Phase 0 冻结）

owner：

- `wallet-service`

接口设计：

```java
public interface KmsSigner {
    /**
     * 对原始交易字节进行签名。
     *
     * @param network ERC20 / TRC20
     * @param fromAddress 平台热钱包地址（由配置决定；一期 ERC20/TRC20 各一个）
     * @param unsignedTx 未签名交易（RLP / Protobuf）
     * @return 签名后的可广播交易字节
     * @throws KmsSignerException 签名失败（key 不可用、HSM 故障等）
     */
    byte[] sign(String network, String fromAddress, byte[] unsignedTx) throws KmsSignerException;
}
```

一期实现：

- `LocalKmsSigner`：从 `falconx.wallet.kms.signing-keys.{network}.private-key-pem` 配置读取私钥，本地签名；适用于 dev / staging
- `KmsSignerStub`：占位实现，调用时直接抛 `UnsupportedOperationException`；生产环境必须显式配置 LocalKmsSigner 或 接入真实 KMS / HSM 实现

注入：

- 通过 `spring.profiles.active` 切换：`dev` 使用 `LocalKmsSigner`；`prod` 必须显式配置否则启动失败
- 私钥读取仅在启动时一次，常驻内存；不允许日志中输出 / 不允许序列化

Nonce 管理：

- ERC20 单实例 `EthNonceManager`（按 `fromAddress` 维度 in-process AtomicLong + 启动时从链上 `eth_getTransactionCount` 拉取）
- TRC20 单实例 `TronNonceManager`（同语义）
- 多副本 wallet-service 部署时由 Redis `falconx:wallet:withdraw:nonce:{network}:{fromAddress}` 串行化（一期 single instance，多副本预留）

详细实施分到 Phase 3-4。
