# FalconX v1 事务与幂等规范

## 1. 目标

统一 FalconX v1 的本地事务边界、最终一致策略和幂等控制点。

## 2. 基本原则

- 一期不引入分布式事务
- 服务内一致性使用本地事务
- 跨服务一致性使用事件和幂等保证
- 所有关键写操作都必须可重试

## 3. 本地事务边界

### `identity-service`

本地事务覆盖：

- 注册用户
- 修改用户状态（含历史 `PENDING_DEPOSIT → ACTIVE` 归一化）
- 记录登录时间

### `market-service`

本地事务覆盖：

- 市场元数据维护
- 交易时间与节假日规则维护
- 低频市场事件的 `t_outbox` 写入

说明：

- Redis 最新价更新不进 MySQL 事务
- 交易时间规则快照写 Redis 不进 MySQL 事务，但必须由 owner 数据变更触发刷新
- 报价历史与 K 线历史写入 ClickHouse
- `falconx.market.price.tick` 直接发 Kafka，不经过 `t_outbox`
- `falconx.market.kline.update` 和低频市场元数据事件通过 `t_outbox` 与本地事务衔接

### `trading-core-service`

本地事务覆盖：

- 账户校验
- 保证金冻结或确认
- 手续费扣减
- 订单写入
- 持仓写入
- 净敞口写入
- 成交写入
- 账本写入
- 强平日志写入

说明：

- `trading-core-service` 是一期最重要的事务边界
- `QuoteDrivenEngine` 的高频读路径只允许读取内存持仓快照和 Redis 最新价，不允许按 tick 直查 MySQL

### `wallet-service`

本地事务覆盖：

- 钱包地址分配
- 原始链交易写入
- 确认数推进
- 游标更新

## 4. 跨服务一致性

跨服务统一采用：

- `本地事务 + Outbox`
- Kafka 事件投递
- 消费端幂等

一期 Outbox 固定采用：

- 服务内定时轮询 `t_outbox`
- 不是 Debezium CDC
- 不是应用代码里直接同步发 Kafka 后再补写数据库
- 公共组件统一放在 `falconx-infrastructure` 的 `outbox` / `inbox` 包中

### 4.1 Outbox 轮询机制

实现路线固定为：

1. 业务事务内写入 `t_outbox`
2. 每个服务本地启动 `OutboxPublisherScheduler`
3. 调度器按固定频率批量轮询待发送事件
4. 成功后标记 `sent`
5. 失败后更新 `retry_count / next_retry_at / last_error`
6. 达到最大重试次数后标记 `dead`

一期推荐参数：

- 轮询间隔：`1s`
- 单批条数：`200`
- 最大重试次数：`10`
- 退避基线：`5s -> 30s -> 120s -> 30m`
- 每档统一叠加 `±20%` jitter，避免同批失败消息在固定时间同时重试
- 超过阈值：标记 `dead`，由运维或补偿任务介入处理

推荐公共包结构：

- `com.falconx.infrastructure.outbox`：`OutboxMessage`、`OutboxRepositorySupport`、`OutboxPublisherScheduler`
- `com.falconx.infrastructure.inbox`：`InboxMessage`、`InboxRepositorySupport`、`InboxIdempotencyGuard`

推荐调度流程：

- 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 选取一批 `pending/failed`
- 在短事务内把状态更新为 `dispatching`
- 提交事务后再调用 Kafka producer
- 成功回写 `sent`
- 失败回写 `failed`

消费者幂等固定采用：

- 低频关键事件使用消费端 `t_inbox` 去重表
- 高频价格 tick 不写 `t_inbox`，幂等由处理逻辑本身或 Redis 短窗口保证
- `market.kline.update` 属于低频关键事件，`trading-core-service` 消费后必须通过 owner `Mapper + XML + Repository` 写入 `t_inbox`
- `eventId` 唯一约束只强制用于低频关键事件
- `t_inbox` 只能在“业务处理成功”或“幂等跳过成立”之后写入；若 owner 业务对象不存在或业务动作未完成，必须让消费失败并走重试，不能提前标记成功

禁止：

- 依赖跨服务同步调用完成一整个业务事务
- 依赖人工补偿作为默认路径

## 5. 幂等键分层

### 5.1 HTTP 写请求

使用：

- `X-Idempotency-Key`

适用：

- 注册
- 下单
- 平仓
- 地址申请

### 5.2 交易业务

使用：

- `clientOrderId`

适用：

- 下单请求去重

### 5.3 钱包链上交易

使用：

- `walletTxId`

适用：

- wallet owner 对外输出的稳定原始交易标识
- trading-core 业务入账事实去重

补充约束：

- `wallet-service` 内部的原始链事实可按 `(chain, tx_hash, log_index)` 拆分
- 跨服务 confirmed / reversed 事件不得再直接以 `(chain, tx_hash)` 作为最终业务幂等键
- 原生币转账固定使用 `log_index = 0`

### 5.4 账本流水

使用：

- `t_ledger.idempotency_key`

适用：

- 资金动作幂等

### 5.5 Kafka 消费

使用：

- `eventId`

适用：

- 事件消费去重

## 6. 一期关键流程要求

### 6.1 下单

规则：

- 接口层校验 `X-Idempotency-Key` 或 `clientOrderId`
- 交易时间校验必须先于保证金冻结执行
- 应用层进入本地事务
- 事务内完成账户、订单、持仓、成交、账本和 `t_risk_exposure` 写入
- 持仓若携带 `takeProfitPrice / stopLossPrice`，必须和开仓一起持久化到 `t_position`
- 事务后通过 `Outbox` 发布订单事件

### 6.2 入金确认

规则：

- `wallet-service` 先确认原始链交易状态
- 生成 `deposit.confirmed` 事件
- `trading-core-service` 幂等消费
- 事务内完成账户余额与账本写入
- 同一事务内写入 `falconx.trading.deposit.credited` 对应的 `t_outbox`

### 6.3 入金事件消费与历史状态归一化

规则：

- `trading-core-service` 完成入账后，事务内写 `t_outbox`，投递 `falconx.trading.deposit.credited`
- `identity-service` 幂等消费（用 `eventId` 去重）
- 事务内检查用户当前状态，若为历史 `PENDING_DEPOSIT`，归一化至 `ACTIVE`，更新 `t_user.activated_at`
- 用户已为 `ACTIVE` 时，消费事件只完成 `t_inbox` 幂等留痕，不改变账户可用状态
- 若用户尚未落库或 owner 业务对象不存在，必须抛错并等待事件重试，不允许把该场景记为已消费
- 幂等键：`eventId`（消费端 Redis 或 DB 去重均可，使用 DB 唯一约束更稳）

### 6.4 实时触发与强平

规则：

- `trading-core-service` 消费价格事件
- 高频 `price.tick` 不落 `t_inbox`
- `price.tick` 的 Kafka 入口允许容器级失败重试，但不得把高频链路改造成 `t_inbox` 持久化消费
- 服务启动时从 DB 装载全部 `OPEN` 持仓到内存快照，并按 `symbol` 分组索引
- 开仓、平仓、强平、TP/SL 修改后必须同步更新内存快照
- `QuoteDrivenEngine` 运行时只读内存快照，不直接查 MySQL
- `price.tick` payload 必须携带 `quoteStatus / qualityReason`；历史消息缺少该字段时按 `stale` 推断
- 只有 `quoteStatus=FRESH` 且交易时间打开的 tick 可以进入成交、TP/SL 或强平判断
- `STALE / NO_QUOTE / MARKET_CLOSED / ABNORMAL` tick 只能更新参考快照或写日志，不得写 `t_trade / t_ledger / t_position` 终态或 `t_liquidation_log`
- 休盘时 market-service 不处理该 `symbol` 报价；trading-core-service 即使收到历史或重放 tick，也必须在触发前二次校验交易时间
- 对订单或持仓做业务级幂等判定
- 如需短窗口去重，优先使用 Redis，避免为 tick 写数据库去重表
- 防止同一价格事件重复触发相同业务动作

#### 6.4.1 CROSS 账户级强平串行化与逐仓重算（STAGE-14D2）

CROSS 账户（`cross_mode.enabled=true`）的强平判据为**账户级 MarginLevel**而非单仓 liqPrice，由 `CrossLiquidationOrchestrator` 编排：

- **user-level Redisson 锁** `cross-liq:{userId}`，`tryLock(0, ...)` 不等待。获取不到（该用户正被另一 tick 评估）即跳过本次（下个 tick 再来），**不阻塞 tick 线程**，避免同一用户多 symbol tick 并发重复账户级评估。
- 锁内评估**只读账户快照**（`AccountMarginStateCache`，不持 DB 行锁）；真正落账由逐仓 `closePositionByTrigger` 内 `SELECT ... FOR UPDATE` 各自获取持仓行锁后立即提交。user-level 锁与单仓 `FOR UPDATE` 维度正交，**不死锁**。
- **逐仓重算闭环**：跌穿后按 `|uPnL(账户币)|` 降序逐仓平，每平一仓即失效账户缓存 + 重新取剩余 OPEN 持仓重算账户级 ML，恢复（ML > stopOut）即止步，避免过度强平。
- **幂等**：逐仓 `closePositionByTrigger` 复用既有 `FOR UPDATE` + `isTerminal` 兜底（已被并发链路平掉返回 null → 跳过继续重算），同一 tick 同一仓位只落账一次。
- **实时 MM**：账户级 ML 重算的维护保证金用实时 fx（mmRate 冻结），FX 不可用降级用开仓冻结 `entry_fx_rate`，不阻断强平判据（见 [状态机规范 §6.3 补充](../domain/状态机规范.md)）。

### 6.5 Swap 结算

规则：

- `market-service` 维护 `t_swap_rate`
- `market-service` 必须把每个 `symbol` 的 `Swap rate` 生效规则快照写入 owner Redis，共享 key 固定为 `falconx:market:swap-rate:{symbol}`
- Redis `Swap rate` 快照固定设置 `25h` TTL，并由 `market-service` 启动预热 + 每日 `UTC 00:00` 定时全量刷新
- `trading-core-service` 只允许读取 owner Redis 快照，不允许跨服务读取 `falconx_market`
- `trading-core-service` 按 `rollover_time` 定时扫描 `OPEN` 持仓
- 结算时必须使用 rollover 时点的 fresh 有效价计算结算名义本金
- `Swap` 结算只接受落在 `rollover ± stale.max-age` 窗口内的最新有效价；超过窗口的后续报价不得拿来补算同一 `rollover`
- 有效价口径固定为 `BUY -> bid`、`SELL -> ask`
- `Swap` 结算金额 = 结算名义本金 × 多/空费率
- 结算金额写 `t_ledger`，必要时写 `t_outbox`
- 账本主幂等键固定为 `swap:{positionId}:{rolloverAt}`
- 若 `rollover` 时点缺少可用 fresh 报价，本轮必须跳过落账并等待下一轮重试；不得写入近似金额
- 对应账本业务类型固定使用：
  - `6=swap_charge`
  - `7=swap_income`
- 一期不引入三倍日和节假日顺延特殊规则
- 首版若没有明确下游消费方，不强制新增 `Swap` Kafka 业务事件；若后续启用，必须通过 owner `t_outbox`
- 本节是正式规则冻结与当前实现口径收敛，不代表 `Swap` 查询展示、业务事件和阶段验收已经完成

### 6.6 负净值保护

规则：

- 强平导致实际亏损超过账户可承受范围时，账户余额最低只能到 `0`
- 超出的平台兜底金额记录到 `t_liquidation_log.platform_covered_loss`
- 不允许出现负余额账户
- 穿仓不形成用户负债，不追收
- 本节已完成规则冻结；当前仓库只在已有实现范围内体现该口径

### 6.7 交易时间校验

规则：

- `market-service` owner 持久化 `t_trading_hours / t_trading_hours_exception / t_trading_holiday`
- `market-service` 启动时把每个 `symbol` 的交易时间快照写入 Redis
- Redis 交易时间快照固定设置 `25h` TTL，并由 `market-service` 每日 `UTC 00:00` 定时全量刷新
- `trading-core-service` 下单前只读 Redis 快照，不跨服务读取 `falconx_market`
- Redis 快照 miss 时默认拒绝开仓，避免在规则不明时放行订单
- 判定优先级固定为：
  1. `t_trading_hours_exception`
  2. `t_trading_holiday`
  3. `t_trading_hours`
- 跨午夜 session 允许使用单条规则表达，运行时必须正确支持“开盘日在前一日、收盘在次日凌晨”的窗口判定
- 非交易时段、节假日全休或人工例外停盘返回 `40008: Symbol Trading Suspended`；该规则适用于开仓和手动平仓，TP/SL 与强平在执行前也必须跳过休盘 tick

### 6.8 逐仓持仓写路径并发保护

规则：

- 追加逐仓保证金、手动平仓、强平执行三类写路径共享同一 `SELECT FOR UPDATE` 模板，统一锁定 owner `t_position` 记录。
- 三类写路径不得使用乐观锁、不得跨记录混合锁定顺序；必须先锁 `t_position` 再锁 `t_account`。
- 追加保证金成功后必须同事务更新 `margin / liquidation_price` 并保持 `status=OPEN`；`liquidation_price` 的重算在同事务内完成。
- 强平执行前必须基于最新 DB 持仓二次校验 `margin / liquidation_price`；若补仓后已不满足强平条件，取消本次强平执行。
- 追加逐仓保证金审计以 `t_ledger.biz_type=10(isolated_margin_supplement)` 和持仓最新快照承载；不写 Outbox、不发 Kafka 业务事件（对应 [逐仓模式改造方案](../process/逐仓模式改造方案.md) §5.2 D2 冻结）。
- 与 [状态机规范](../domain/状态机规范.md) §6 持仓状态机保持一致：追加逐仓保证金不触发状态迁移。

### 6.9 Stage 7A 后续逐仓范围的事务与幂等冻结

对应 [逐仓模式改造方案](../process/逐仓模式改造方案.md) §5.2 的 **D2 冻结结论**：

- 追加保证金不新增任何 Kafka topic，也不新增任何 Outbox 事件类型；本文件 §4 Outbox 约束不为该动作开特例。
- Stage 7A 整阶段验收（`STAGE7A-ISOLATED-02`）必须保持三类写路径共享 §6.8 模板，不得引入独立并发策略。

### 6.10 写账三列口径与自洽性（STAGE-14B 货币转换）

对应 [数据库设计](../database/falconx一期数据库设计.md) §4.3（V28/V29）与 [STAGE-14 master](../design/STAGE-14-MULTICURRENCY-AND-CROSS-MARGIN-MASTER-design.md)。

规则：

- 每条 `t_ledger` 写入必须同事务填齐货币四口径：
  - `amount` = 账户币（account currency）金额，**驱动 balance / frozen 余额变更**
  - `original_amount` = 原币（quote currency）金额
  - `original_currency` = 该笔账的 quoteCurrency 代码
  - `fx_rate_at_settlement` = 结算/成交/开仓时刻的 `fx(quoteCurrency → accountCurrency)`
- **自洽性约束**：每条账须满足 `original_amount × fx_rate_at_settlement = amount`（按账户币精度舍入）。
- margin 账与 fee 账各自携带自身查询时刻的 fxRate（fee 账用 `feeFxRate`），不得复用对方 fxRate，保证各自三列数学自洽。
- `t_position.entry_fx_rate` 记录开仓时 `fx(quote→account)` 快照，**仅审计留痕，不参与强平价 / 保证金重算**。
- **例外（预期审计行为，非数据错误）**：§6.6 负净值保护触发时，`amount` 取封顶后的账户币值（不允许负余额），此时三列保留完整原值，`amount ≠ original_amount × fx_rate_at_settlement` 是预期结果。
- **FX 不可用降级口径**：
  - 开仓阶段 FX 不可用 → 拒单（错误码 `30073 FX_RATE_UNAVAILABLE`，见 [统一接口文档](../api/FalconX统一接口文档.md)），不落账。
  - 平仓 / 强平 / Swap 等被动结算阶段 FX 不可用 → 不阻断结算：`fx_rate_at_settlement` 退化为 `1`、`original_currency` 仍如实记录真实 quoteCurrency、并打 WARN。
- 算法层 FX 真源统一为 trading 侧 `FxRateService`；写账链路不得绕过它另取汇率。

### 6.11 MarginLevel 实时重算与 StopOut 强平串行（STAGE-14C1）

对应 [状态机规范](../domain/状态机规范.md) §6.2/§6.3 与 [数据库设计](../database/falconx一期数据库设计.md) §4.3（V30/V31/V32）。

规则：

- `QuoteDrivenEngine` 每 tick 对受影响用户的单仓重算 MarginLevel（ISOLATED 口径见状态机 §6.2）。重算输入为内存快照 + 实时报价，**判定路径只读账户内存缓存**（balance/frozen/marginUsed，约 1s 级别），不为高频判定逐 tick 查 MySQL。
- **判定与写分离的强一致约束**：内存缓存仅用于「是否触发」判定；一旦判定触发强平，实际平仓写路径必须经 `closePositionByTrigger` 的 `SELECT FOR UPDATE` 锁定 owner `t_position` 记录并基于最新 DB 二次校验后再写终态，保证强一致（与 §6.8 三类写路径共享同一锁模板）。
- **StopOut 双触发归一**：`liqPrice` 价格命中 或 单仓 `MarginLevel ≤ stopOutLevel`，任一即按 `LIQUIDATION` 强平；同一 tick 同一仓位只调用一次 `closePositionByTrigger`，已 `CLOSED` / 重复触发由其内部 `FOR UPDATE` 兜住，防重复强平。
- 强平成功后必须失效该用户账户内存缓存（balance/frozen/marginUsed 已变），下次判定重新加载。
- 仅 `MarginLevel` 触发（非纯 liqPrice）才补发 `STOP_OUT_TRIGGERED` 站内信并填真实 MarginLevel 数值；纯 liqPrice 触发不发。
- MarginCall 告警（`MARGIN_CALL_TRIGGERED`）+ 同用户 5min 节流在 `MarginLevelMonitor` 内完成，不在强平路径执行；`MarginLevel == null`（FX 不可用 / 无持仓 / 除零）按 `HEALTHY` 处理，StopOut 不触发，`liqPrice` 仍独立生效。
- MM 用开仓冻结 `mm_rate_at_open`（实时 MM 留 STAGE-14D）；CROSS 账户级强平判据延 STAGE-14D。

## 7. 非法实现示例

下面做法明确禁止：

- 网关直接写业务库
- 一个 HTTP 请求横跨多个服务数据库做事务
- 没有幂等键的下单写接口
- 消费 Kafka 时不做 `eventId` 去重
- 链上交易只靠 Redis 去重、不做数据库唯一约束
- 业务代码直接调用 Kafka producer 代替 Outbox
