# BBook 一期完成执行路径

> 本文件是 FalconX BBook 一期完成判定项的剩余执行路径。后续开发严格按本文件推进，按阶段顺序、按任务工单执行，不得跳跃、不得自行扩张范围。
>
> 阶段状态、阻断项与下一步顺序仍以 [`当前开发计划`](../../setup/当前开发计划.md) 为最终真源；本文件是该真源的剩余路径细化与执行手册。

---

## 1. 目的与适用范围

本文件解决一个具体问题：FalconX 当前已完成 `Stage 1-7A`、`USER-WS-REALTIME-01` 首版、`BBOOK-RISK-CONTROL-01`、`BBOOK-RISK-GUARD-01`，距 [BBook 一期完成开发计划 §6 完成判定](../BBook一期完成开发计划.md) 仍有具体差距。本文件把剩余差距拆成可独立执行、可串行验收的任务，作为后续开发的执行入口。

适用对象：

- 后续承接 BBook 一期开发的 Commander 与 subagent
- 阶段验收时核对完成度的回归
- 单次工作交接时的最小阅读集补充

不适用：

- 业务规则、接口契约、数据库 schema、Kafka 事件 payload、状态机迁移、错误码 / 状态码、安全规范的正式定义（仍以 [`AGENTS.md`](../../../AGENTS.md) §2 引用的正式规范为准）
- 一期不在 FalconX 范围的能力（详见 §11）

## 4. 阶段 1：CROSS 保证金真实执行收尾

### 4.1 重构 CROSS 强平校验旁路

任务编号：`CROSS-MARGIN-EXEC-01-A`

#### 目标

`TradingPositionCloseApplicationService.closePositionByTrigger()` 中"信任调用方的 CROSS 分支"是当前会话引入的临时设计，需要重构为显式双轨入口，避免 ISOLATED 与 CROSS 的关闭语义混淆。

#### 实施步骤

1. 在 `TradingPositionCloseApplicationService` 拆分为两个入口：
   - `closePositionByPositionLevelTrigger(positionId, reason, snapshot)`：用于 ISOLATED 强平、TP、SL，内部调用 `PositionTriggerRuleEvaluator.evaluate()` 复核
   - `closePositionByAccountLevelLiquidation(positionId, snapshot, accountEvidence)`：用于 CROSS 账户级强平，跳过 per-position 评估器，要求传入账户级权益证据
2. 移除现有 `if (closeReason == LIQUIDATION && marginMode == CROSS)` 特殊分支
3. 调用方调整：
   - `QuoteDrivenEngine` 内的 ISOLATED 强平、TP、SL 调用入口 1
   - `CrossMarginLiquidationApplicationService.evaluateAndLiquidate()` 调用入口 2，构造 `accountEvidence`，包含 `equity`、`crossMaintenance`、`mostLosingPnl`、`totalUnrealizedPnl`、`accountSnapshotTs`
4. 数据库变更：`t_liquidation_log` 新增字段 `evidence_json JSON DEFAULT NULL`（V Schema 迁移按当前最新版本号顺延）
5. 强平日志写路径在 CROSS 分支落入 `evidence_json`，ISOLATED 分支保持空
6. 单元测试新增：双入口的契约测试、CROSS 入口缺失 evidence 时的拒绝行为
7. 集成测试调整：`TradingCrossMarginIntegrationTests` 中现有 6 个用例确认仍通过

### 5.1 跨服务联动方案冻结

任务编号：`WALLET-REGISTER-ADDRESS-01-A`

#### 目标

不进入代码前先冻结失败语义、事件契约、补偿机制。

#### 冻结决策

- **触发方式**：identity 注册事务提交后，通过 Outbox 发布 Kafka 低频事件 `falconx.identity.user.registered`
- **不使用同步 RPC**：避免注册接口耦合 wallet 可用性
- **事件 payload**：`userId`、`uid`、`email`、`registeredAt`、`clientIp`、`settlementToken`、`groupCode`
- **分区键**：`userId`
- **wallet 消费方语义**：
  - 已分配 → 直接 ack
  - 未分配 → 派生 TRC20 + ERC20 写 `t_wallet_address`，事务内
  - xpub 缺失或派生失败 → 写入新表 `t_wallet_address_provision_dlq`，按 Outbox 重试策略
  - DLQ 重试达上限 → 写告警日志，等待人工干预
- **注册不回滚**：wallet 失败不影响注册成功；用户进入入金页时仍可走 `ensure` 接口兜底分配
- **identity 不读 wallet 数据**：identity 不感知地址分配状态

- [`Kafka 事件规范`](../../event/Kafka事件规范.md)：新增 topic 定义、payload 字段、幂等键、消费 owner

### 5.3 wallet 消费注册事件并幂等分配地址

任务编号：`WALLET-REGISTER-ADDRESS-01-C`

#### 目标

wallet 监听 `falconx.identity.user.registered`，幂等触发地址派生。

#### 实施步骤

1. wallet 新增 Kafka 消费者 `IdentityUserRegisteredEventConsumer`：
   - 回调线程立即提交线程池（按 [`AGENTS.md`](../../../AGENTS.md) §3.8.2 跨服务回调要求切换执行器）
   - 恢复 traceId 上下文
2. 新增 `WalletAddressProvisionApplicationService.provision(userId)`：
   - 查 `t_wallet_address` 是否已存在 → 已存在直接返回
   - 调 `XpubWalletAddressDerivationService` 派生 TRC20 + ERC20
   - 事务内写入 `t_wallet_address`
   - xpub 缺失 / 派生失败 → 写入 `t_wallet_address_provision_dlq`（含 `userId`、`reason`、`retry_count`、`next_retry_at`、`last_error_message`）
3. 后台 DLQ 重试任务：
   - 每 5 分钟扫 `t_wallet_address_provision_dlq` 中 `next_retry_at <= now AND retry_count < max_retries`

### 8.3 LP 长断线保护策略

任务编号：`MARKET-COMPLETENESS-01-C`

#### 目标

LP reconnect 机制存在，但长时间断线时业务侧无自动响应（继续接受订单但所有报价 stale）。改为自动激活全局风控保护。

#### 实施步骤

1. `market-service` 监控 LP 连接状态：
   - 用现有 `market.lp.provider.connected` / `market.lp.provider.disconnected` 信号
   - 增加监控：连续 N 分钟（默认 5 分钟）无 `price-compression` 即视为长断线
2. 长断线触发：通过 Kafka 发布 `falconx.market.lp.outage` 事件，payload `outageDuration`、`lastQuoteTs`
3. trading-core 消费该事件：
   - 自动激活 `GLOBAL_PAUSE` 风控动作，来源标记为 `LP_OUTAGE`
   - 记录到 `t_risk_control_action`
4. LP 恢复后（连续 1 分钟正常推送）：
   - 通过 Kafka 发布 `falconx.market.lp.recovered`
   - trading-core 自动停用 `LP_OUTAGE` 来源的 `GLOBAL_PAUSE`
   - 已有的 `GLOBAL_PAUSE`（其他来源激活的）保持不变
5. 配置项：
   - `falconx.market.lp.outage-threshold`（默认 5m）
   - `falconx.market.lp.recovery-threshold`（默认 1m）
6. 集成测试：模拟 LP 断线 + 恢复全流程

#### 涉及文件

- 新增：`MarketLpHealthMonitor.java`
- 新增：`MarketLpOutageEventPublisher.java`
- 修改：`SocketIoLpMarketQuoteProvider.java`（暴露连接状态信号）
- 新增：`MarketLpOutageEventConsumer.java`（trading-core 侧）
- 修改：`DefaultTradingRiskService.java`（接入 LP_OUTAGE 来源）
- 新增测试：`MarketLpHealthMonitorTests.java`、`TradingLpOutageRiskControlIntegrationTests.java`

## 13. 执行原则

1. **按阶段顺序推进**：阶段间依赖关系见 §3 阶段总览。不得跳跃执行。
2. **任务级独立提交**：每个子任务（如 `CROSS-MARGIN-EXEC-01-A`）形成一个独立 Git commit，便于回滚。
3. **遇到契约变更必须先确认**：如果实施过程中发现需要修改本路径未冻结的接口、数据库 schema、Kafka 事件 payload、状态机或错误码，必须先暂停实施、向用户确认、再继续。
4. **不得自行扩张范围**：任何 §11 范围外的能力，即使发现"顺手补一下也不复杂"，也必须新增任务并经用户确认后再做。
5. **测试优先验证**：每个任务先写测试再写实现（按 [`Karpathy 式 AI 编码行为准则`](../Karpathy式AI编码行为准则.md)），测试通过即视为该任务的"成功标准"。
6. **本文件是真源**：执行过程中如本文件与其他文档冲突，以本文件为准；同时反向修正其他文档。
7. **完成判定一票否决**：任意一项 §2 完成判定项未达成，整个 BBook 一期不能宣告 "开发完成"。
