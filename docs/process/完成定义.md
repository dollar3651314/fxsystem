# FalconX v1 完成定义

## 1. 目的

本文件用于定义 FalconX 在实施阶段中“一个任务什么情况下才算完成”。

它适用于：

- 功能开发
- 接口开发
- 事件开发
- 数据库变更
- 文档修订

## 2. 所有任务的共通要求

任一任务要标记为完成，至少满足：

1. 实现符合当前架构与 owner 边界。
2. 涉及文档的变更已同步完成。
3. 输出结果与文档一致。
4. 未擅自扩展用户未授权的范围。
5. 若本轮修改了仓库内容，已形成可回滚的 Git 提交点；若用户要求同步远程，已推送到 `GitHub` 远程仓库。
6. 若本轮属于常规开发任务，交付 commit 已落在 `main` 分支；若涉及 `main`，已得到用户明确授权。

补充要求：

- 若当前实现仍基于 `In-Memory Repository`、`stub provider / listener` 或日志型 publisher，必须在结论和计划文档中显式说明。
- 不允许把“骨架级完成”表述成“真实基础设施已接入”或“可用于生产”。
- 若任务源自问题清单、审计文档或补充事项文档，必须先完成“问题是否真实存在”的核对，再进入修复。
- 若工作区存在与本轮无关的未提交修改，必须先隔离，再为当前任务生成独立回滚点。
- 若任务未要求处理其他分支，实施前默认应在 `main` 分支开展。

## 2.1 代码类任务附加条件

若任务包含业务代码、测试代码、脚本或配置实现，除满足共通要求外，还必须满足：

1. 代码带有与复杂度相称的注释。
2. 关键业务节点具备符合规范的日志。
3. 对应测试已补齐并通过。
4. 已说明本轮实际验证范围，不能只写命令名。

## 2.2 文档类任务附加条件

若任务是纯文档、规范或计划修订，除满足共通要求外，还必须满足：

1. 表述、阶段口径和引用链接已交叉核对。
2. 不得在不同文档中保留相互冲突的现行规则。
3. 纯文档任务默认不要求补代码注释、业务日志或跑全仓测试；若未执行代码验证，必须明确说明。

## 2.3 问题清单 / 审计类任务附加条件

若任务起点是问题清单、审计记录或补充整改项，除满足共通要求外，还必须满足：

1. 已先核对问题是否真实存在，再决定是否改代码。
2. 交付结论必须区分：
   - 真实存在，需要修复
   - 已修复，仅需同步文档
   - 不成立，不得误修
3. 原问题文档或统一问题清单状态已同步更新。

## 3. 阶段与计划任务完成条件

若本次任务会影响阶段状态或实施顺序，除满足共通要求外，还必须满足：

1. [当前开发计划](../setup/当前开发计划.md) 已同步更新。
2. 已明确写出本阶段当前属于“骨架 / stub”还是“真实基础设施接入”状态。
3. 阶段验收同时包含：
   - 业务链路验证结论
   - 对应命令或测试项
4. 已写明下一阶段范围，不能留下计划真空。
5. 若阶段内引入 Redis 快照、Kafka 事件或跨服务共享 JSON 结构，必须写明 TTL / 刷新 / cache miss 策略与兼容性结论。

## 4. 接口任务完成条件

接口任务除满足共通要求和代码类任务附加条件外，还必须满足：

1. 接口已在目标环境完成开发验证。
2. 请求头、请求参数、响应结构、错误码已固定。
3. 日志点已按规范落位。
4. 已更新统一接口文档：
   - [FalconX统一接口文档](../api/FalconX统一接口文档.md)

以下任一未完成，接口任务不得标记完成：

- 未更新统一接口文档
- 未给出请求/响应示例
- 未给出测试结论

## 4.A 三端任务完成条件（强约束）

按用户冻结的"功能完成 = 客户端 + 后端服务 + 管理端三端完成"硬约束（2026-05-08 范围调整后），任何业务功能交付必须满足以下三端齐全：

| 端 | 必须输出 | 角色 |
| --- | --- | --- |
| **客户端** | falconx-frontend 实现 + `npm run test` + `npm run lint` + `npm run build` + 桌面/移动浏览器 QA 截图 | R5 客户端前端实施者 |
| **后端服务** | 业务服务（identity / market / trading-core / wallet）实现 + 单元测试 + 集成测试通过 | R4 业务后端实施者 |
| **管理端** | falconx-console-service 后端 API + falconx-console-frontend UI（含用户/角色/菜单/按钮 RBAC 控制点）+ QA 截图 | R9 管理端后端 + R10 管理端前端 |

按 [`AI工作模式`](./AI工作模式.md) §5.1 与 [`fullstack-bundle.md`](../../.agents/templates/fullstack-bundle.md)，**任意一项未完成均不得标记完成**：

1. R2 Contract Designer 输出的契约（含客户端 API、管理端 API、Kafka、DB）已被用户确认
2. R3 UI/UX Designer 输出的客户端 + 管理端双端设计方案已被 R1 接收
3. R6 Test Designer 测试用例先于实现写出（含三端 E2E）
4. R4 后端服务实现 + 测试通过
5. R5 客户端前端实现 + 三件套通过 + 浏览器 QA 截图
6. R9 管理端后端实现 + 测试通过
7. R10 管理端前端实现 + 三件套通过 + 浏览器 QA 截图
8. 至少一条 E2E 测试覆盖客户端调用 → 后端 → 管理端可见整链
9. R8 Doc Synchronizer 完成文档同步（含 `FalconX 统一接口文档` + `管理端接口规范`）
10. R7 QA Verifier 最终验证报告完整
11. 形成单一 Git commit（含三端代码 + 文档 + 测试）

**例外**：

- 纯运维 / 内部维护任务（如 LP 历史 K 线回填、对账脚本、可观测性接入）若无客户端 / 管理端入口，由 R1 在任务启动时显式声明豁免
- 阶段 0（CROSS 回滚 / 完成定义升级 / 角色扩展 / 文档归档）作为基础设施任务，豁免"管理端"要求，但仍需满足"前后端"二端
- 阶段 1（管理后台地基）的"管理端骨架"是单端任务，豁免本节的三端要求；阶段 1 完成后，后续所有功能必须严格满足三端

R1 不得任意豁免有客户端入口的任务的"管理端"要求。

## 5. 数据库任务完成条件

数据库相关任务除满足共通要求和代码类任务附加条件外，还必须满足：

1. 数据库设计文档已更新。
2. SQL 蓝图已更新。
3. owner 边界未被破坏。
4. 若进入实现阶段，Flyway migration 目录与命名规则已同步落位。
5. 若修改的是作为“基线蓝图”的原始 SQL 文件，同时必须确认运行时 migration 或测试数据库初始化没有出现语义漂移。
6. 若修改的是原始 `V1 / V2` 这类 Flyway 基线脚本，必须同时处理 checksum 影响；验证时应使用新的隔离测试库，或在得到明确授权后执行 repair，不能继续复用已应用旧 checksum 的测试库。

## 6. 事件任务完成条件

事件相关任务除满足共通要求和代码类任务附加条件外，还必须满足：

1. Topic 命名已纳入 Kafka 事件规范。
2. payload 已定义。
3. 分区键与幂等规则已明确。
4. 发布方和消费方 owner 已明确。
5. 若 payload 或缓存结构新增字段，必须验证消费方兼容性，不得把反序列化风险留到联调阶段。

## 7. 提交前自检清单

提交前至少确认：

- 是否遵守 AGENTS 规则
- 是否更新了必要文档
- 若本轮包含代码实现，是否补齐测试
- 若本轮包含代码实现，是否补齐日志
- 是否更新统一接口文档
- 是否说明了验证结果
- 是否有超出用户明确授权范围的内容；若有，是否已经先获得确认
- 若本轮涉及阶段状态变化，是否已同步更新当前开发计划并写明当前实现级别
- 若本轮涉及问题清单修复，是否已回写原问题文档状态
- 若本轮涉及 Redis / Kafka / 跨服务共享 JSON，是否已写明并验证 TTL、刷新、cache miss 和兼容性
- 是否避免并行执行会互相影响的验证命令（例如 `mvn test` 与 `mvn clean compile`）
- 若本轮修改了仓库内容，是否已经生成独立的 Git 回滚点；若用户要求同步远程，是否已经 push 到 `GitHub`
- 若本轮属于常规开发，是否确认提交位于 `main` 分支；若处理 `main`，是否已得到用户明确授权

## 7.A 4 条 Karpathy 编码准则强制自检（永久生效）

每次代码任务交付前，必须自检 [`AI工作模式`](./AI工作模式.md) §1.2 + [`Karpathy 式 AI 编码行为准则`](./Karpathy式AI编码行为准则.md) 的 4 条准则。任意违反即视为完成失败：

- [ ] **编码前先思考**：编码前已陈述假设、未默默选择解读、不确定时已询问
- [ ] **简洁优先**：实现是问题所需的最小代码、无未要求的功能/抽象/灵活性
- [ ] **精准修改**：每行改动都能追溯到用户请求、无顺手重构/格式 churn
- [ ] **目标驱动执行**：已转换为可验证目标、并执行了验证（不是"应该可以"）
