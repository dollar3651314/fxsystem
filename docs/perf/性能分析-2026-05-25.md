### 本轮新发现的"半修"问题（需要追加修复）

#### [P0-半修] MarketChart `useEffect([currentQuotePrices])` 仍每 tick 调 autoScale x3

- 文件：`falconx-frontend/src/features/market/MarketChart.tsx:340-343`
- 现状：`c7ec2cf` 把 candles 引用从每 tick 触发改为 kline 粒度，但 `currentQuotePrices` 仍是每条 quote 触发的状态，依赖它的这个 effect 每 tick 调 3 次 `priceScale().applyOptions({autoScale:true})`
- 影响：lightweight-charts 仍按报价频率重算 priceScale，CPU 占用与 c7ec2cf 之前相比下降 < 50%
- 推荐修复：debounce 100-200ms；或仅在 quote 价位真实超出当前 priceRange 时才触发 autoScale；保留 `setData` 后的 autoScale（L700-702）一次性应急

#### [P1-半修] Prometheus 端点未启用，新增 Gauge 无法被外部抓取

- 文件：各 service `application.yml`（`management.endpoints.web.exposure.include`）+ 顶层 / 各 service `pom.xml`
- 现状：`5a7a21a` + `fdae604` 注册了 tick executor / WebSocket session / push backlog 三类 Gauge，但 actuator 仍只暴露 `health,info,metrics,loggers`；也无 `micrometer-registry-prometheus` 依赖
- 影响：现在 Gauge 只能通过 `/actuator/metrics/{name}` 查单值，外部 Prometheus / Grafana 抓不到时间序列；运维手册里的"观测入口"实际上跑不通
- 推荐修复：① pom 顶层 dependencyManagement 加 `io.micrometer:micrometer-registry-prometheus`，业务 service 引依赖；② `application.yml` `exposure.include` 加 `prometheus,threaddump,heapdump`

#### [P1-未变] market `RedisMarketReferenceQuoteRepository.saveLastValid` 8 次 hash put

- 与原报告 §3 一致，未修复。trading 端 `RedisTradingQuoteSnapshotRepository.save` 同样仍 8 次 put（17a7d29 没动写路径）
- 推荐修复仍是 `putAll(Map)` 或 Lua 脚本一次原子完成

## 2. 后端 - 数据库 / 事务 / MyBatis

### [P0] `t_inbox` / `t_outbox` 表无清理任务
- 运行时观测：`t_inbox` 188万行 724MB / `t_outbox` 63.5万行 283MB
- 现象：Kafka 幂等 inbox + outbox 设计正确，但只有 outbox 状态机推进、没有"已处理超 N 天的记录归档/删除"任务
- 影响：单次 inbox/outbox 查询响应时间持续上升；MySQL buffer pool 被这两张表挤占；Innodb_row_lock_waits 在这两张表上累积
- 推荐修复：加每日定时 job 把 status=COMPLETED/PROCESSED 且 created_at < now-7d 的记录移到归档表或直接删除；监控两表行数告警阈值 100w

### [P0] MySQL 慢查询日志关闭 + `long_query_time=10s`
- 文件：MySQL `falconx-mysql` 容器配置；`deploy/mysql/init/*` 或 compose env
- 现象：无法定位实际慢查询，10597 次 row lock waits 来源不明
- 影响：所有"DB 慢"问题都是盲修
- 推荐修复：`SET GLOBAL slow_query_log=ON; SET GLOBAL long_query_time=1;`，docker compose mysql 段加 `command: --slow-query-log=1 --long-query-time=1 --log-slow-extra=1`

### [P0] trading 下单链路三次 `SELECT FOR UPDATE` 同一账户行
- 文件：`TradingOrderPlacementApplicationService.java:126`、`TradingAccountService.java:49`
- 现象：`getOrCreateAccountForUpdate()` → `reserveMargin()` → `chargeFee()` → `confirmMarginUsed()` 同一事务内多次 SELECT+UPDATE 同一账户行
- 影响：高 TPS 用户行锁竞争（运行时 10597 row_lock_waits 大概率来自这里）
- 推荐修复：合并为单 SQL `UPDATE t_account SET balance = balance - ?, frozen = frozen + ?, margin_used = margin_used + ? WHERE id = ? AND balance >= ?`，配合余额校验

## 6. 后端 - trading 交易热路径

### [P0] `DefaultTradingRiskService.evaluateUserExposureLimit()` 扫所有 open 持仓 + 逐 symbol Redis 查

- 影响：任一表慢就整事务卡，内存快照已变但 DB 回滚 → 幽灵状态
- 推荐修复：清算/成交日志拆 outbox 异步落盘，事务只保账户+持仓+outbox 原子

### [P0] `QuoteDrivenEngine` 每 tick 全表迭代 open positions

### [P1] `QuoteDrivenEngine.triggerPriceAlerts/PendingOrders` 全表扫
- 文件：`QuoteDrivenEngine.java:334, 357`、`TradingPendingOrderTriggerMapper.xml:68-73`

### [P1] ClickHouse JDBC 无连接池配置
