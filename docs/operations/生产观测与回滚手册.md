## 2. 热路径指标

### 2.1 market-service 行情入口

| 指标 | 语义 | 失败判据 |
| --- | --- | --- |
| `falconx.market.quote.pending.size` | 等待 flush 到 ClickHouse 的 quote tick 数 | `pending.size / queue.max >= 0.8` 持续 30 秒 |
| `falconx.market.quote.queue.max` | quote tick 队列硬上限 | 用作队列水位分母 |
| `falconx.market.quote.dropped.total` | ClickHouse 写入慢于 LP 推送时被容量保护丢弃的 tick 累计数 | 5 分钟窗口增量 `> 0` |
| `falconx.market.kafka.publish.duration` | market Kafka 发布耗时，tag: `topic/eventType/outcome` | p95 `> 500ms` 持续 5 分钟 |
| `falconx.market.kafka.publish.failures` | market Kafka 发布失败计数 | 5 分钟窗口增量 `> 0` |

Actuator 查询示例：

```bash
curl -fsS http://localhost:18082/actuator/metrics/falconx.market.quote.pending.size
curl -fsS http://localhost:18082/actuator/metrics/falconx.market.quote.dropped.total
curl -fsS http://localhost:18082/actuator/metrics/falconx.market.kafka.publish.duration
```

### 2.2 trading-core-service tick 消费

| 指标 | 语义 | 失败判据 |
| --- | --- | --- |
| `falconx.trading.tick.worker.queue.total` | 所有 symbol worker 总排队任务数 | `> 1000` 持续 30 秒 |
| `falconx.trading.tick.worker.queue.size` | 单 worker 排队任务数，tag: `worker` | 单 worker `> 500` 持续 30 秒 |
| `falconx.trading.tick.queue.delay` | Kafka listener submit 到自管 worker 开始执行的排队延迟 | p95 `> 200ms` 持续 5 分钟 |
| `falconx.trading.tick.engine.duration` | QuoteDrivenEngine 实际处理耗时，tag: `symbol/outcome` | p95 `> 300ms` 持续 5 分钟 |
| `falconx.trading.tick.consumer.duration` | listener 等待整条 tick 完成的总耗时 | p95 `> 500ms` 持续 5 分钟 |
| `falconx.trading.tick.consumer.failures` | tick 消费失败计数，tag: `symbol/reason` | 5 分钟窗口增量 `> 0` |
| `falconx.trading.tick.triggered.actions` | tick 触发的强平 / TP / SL 等动作计数 | 非失败指标；用于解释订单/持仓突增 |

### 2.3 Kafka lag 与 WebSocket backlog

Kafka lag 当前由 Kafka 自身工具或外部 exporter 采集，不从业务 JVM 反推：

```bash
kafka-consumer-groups --bootstrap-server localhost:9092 \
  --describe --group falconx-trading-core-service
```

失败判据：

- `falconx.market.price.tick` lag 持续增长 3 分钟，或 lag `> 50000`
- `falconx.market.kline.update` lag `> 1000`
- wallet / withdraw / kyc 低频事件 lag `> 100`

WebSocket 当前以发送失败日志和连接数限制为主。出现以下 fingerprint 时必须告警：

```bash
docker compose logs --since=5m market-service | grep -E "market.websocket.*failed|market.websocket.*limit"
docker compose logs --since=5m trading-core-service | grep -E "trading.websocket.*failed|trading.quote.tick.*push.failed"
docker compose logs --since=5m gateway | grep -E "gateway.websocket.*failed|websocket.*limit"
```

服务内 WebSocket 指标：

| 指标 | 语义 | 失败判据 |
| --- | --- | --- |
| `falconx.market.websocket.sessions.active` | market-service 活跃 WebSocket 会话数 | 异常突增或接近预期容量上限 |
| `falconx.market.websocket.subscriptions.indexed` | market-service `channel + symbol` 索引订阅关系数 | 与活跃会话数不匹配或持续异常增长 |
| `falconx.market.websocket.buffer.bytes` | market-service `ConcurrentWebSocketSessionDecorator` 当前待发送 buffer 总字节数 | 持续增长 3 分钟，或接近 `activeSessions * 512KiB * 0.8` |
| `falconx.gateway.websocket.proxy.sessions.active{upstream}` | gateway WebSocket 代理层当前活跃 bridge 数（`upstream`=market\|trading） | 异常突增或与上游 `sessions.active` 长期背离 |
| `falconx.gateway.websocket.proxy.messages.total{upstream,direction}` | gateway 代理成功转发帧数（`direction`=client_to_upstream\|upstream_to_client） | 速率骤降至 0（链路 stall）或与活跃 bridge 数严重不匹配 |

> gateway 是响应式 pass-through 桥接，无 servlet 式显式 buffer。Reactor pipeline 的真实「待转发 backlog / pending demand」无法低风险地从链路取出（需自定义 Subscriber 介入背压），故 gateway 侧不暴露真 backlog，而以「活跃 bridge 数」+「按方向转发帧速率」作为近似拥塞判据。
| `falconx.trading.websocket.sessions.active` | trading-core 活跃 WebSocket 会话数 | 异常突增或接近预期容量上限 |
| `falconx.trading.websocket.user.subscriptions.indexed` | trading-core `userId + channel` 用户订阅索引关系数 | 与活跃用户会话数不匹配或持续异常增长 |
| `falconx.trading.websocket.admin.subscriptions.indexed` | trading-core admin channel 订阅索引关系数 | 与活跃 admin 会话数不匹配或持续异常增长 |
| `falconx.trading.websocket.push.queue.size` | trading-core WebSocket 单线程推送 executor 待发送任务数 | `> 1000` 持续 30 秒 |
| `falconx.trading.websocket.buffer.bytes` | trading-core `ConcurrentWebSocketSessionDecorator` 当前待发送 buffer 总字节数 | 持续增长 3 分钟，或接近 `activeSessions * 512KiB * 0.8` |

Actuator 查询示例：

```bash
curl -fsS http://localhost:18082/actuator/metrics/falconx.market.websocket.buffer.bytes
curl -fsS http://localhost:18083/actuator/metrics/falconx.trading.websocket.push.queue.size
curl -fsS http://localhost:18083/actuator/metrics/falconx.trading.websocket.buffer.bytes
```

## 3. 告警分级

| 级别 | 条件 | 处理时限 |
| --- | --- | --- |
| P0 | 健康检查 DOWN、Kafka price.tick lag 持续增长、market quote dropped 增量 > 0、trading tick queue.total 持续 > 1000 | 5 分钟内确认是否降级或回滚 |
| P1 | Kafka 发布 p95 > 500ms、tick engine p95 > 300ms、钱包 RPC health DOWN、LP 10 秒无报价 | 15 分钟内定位依赖或扩容 |
| P2 | WARN 日志突增、单 symbol worker queue.size > 500、recon unmatched 接近阈值 | 当班处理 |

> 📌 **告警规则即代码**：上述 §2 指标失败判据与本节 P0/P1/P2 分级已落成机器可执行的 Prometheus 抓取配置 + 告警规则 + Alertmanager 路由 + Grafana 仪表盘，见 [`deploy/monitoring/`](../../deploy/monitoring/README.md)（19 条规则，promtool 单测全过 + 本地告警链路实跑验证，证据 [PROD-OPS-EVIDENCE-MONITORING-2026-06-02](../test/archive/PROD-OPS-EVIDENCE-MONITORING-2026-06-02.md)）。生产/演示档把 `prometheus.yml` 的 target 改为服务 DNS 名、Alertmanager receiver 改为真实集成（凭据外部注入）即可。p95 延迟类规则当前用 Timer 的 `_seconds_max` 作保守代理，真 p95 需后续开 `management.metrics.distribution.percentiles-histogram`。

## 5. 回滚步骤

### 5.1 仅代码回滚

适用：未新增 DB migration、Kafka payload、接口契约或配置必填项。

```bash
git revert <bad_commit>
mvn -pl <changed-module> -am test
git push origin main
```

服务侧按部署形态回退：

```bash
# jar 方式
systemctl stop falconx-trading-core-service
cp /opt/falconx/releases/<previous>/falconx-trading-core-service.jar /opt/falconx/current/
systemctl start falconx-trading-core-service

# docker compose 方式
docker compose pull trading-core-service
docker compose up -d trading-core-service
```

### 5.2 含数据库 migration 的回滚

禁止直接删除已执行的 Flyway migration。必须走以下之一：

1. 若 migration 只新增兼容字段 / 表：先回滚代码，保留 schema。
2. 若 migration 引入错误数据或破坏查询：新增 reverse migration，经 R2 确认后部署。
3. 若需恢复备份：先停止写流量，再按 DBA 备份恢复流程执行。

回滚后必须重新跑：

```bash
java -jar falconx-canary/target/falconx-canary-1.0.0-SNAPSHOT.jar health-all
java -jar falconx-canary/target/falconx-canary-1.0.0-SNAPSHOT.jar login
java -jar falconx-canary/target/falconx-canary-1.0.0-SNAPSHOT.jar recon
```
