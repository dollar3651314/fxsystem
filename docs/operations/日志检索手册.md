# FalconX 日志检索手册（STAGE-11-OBS-RECON §11.3，2026-05-18）

> 本文档侧重运维 / SRE / Oncall 在排查问题时**如何反查日志**，与 [`日志打印规范`](../architecture/日志打印规范.md)（侧重业务代码**如何写入**日志）形成"写 + 查"双手册组合。
>
> 适用范围：本地 docker-compose / WSL dev / 生产 k8s 三种部署模式；不绑定具体日志后端（Splunk / ES / Loki 等），仅给 `grep` / `kubectl logs` / `journalctl` 三类基础工具的查询模板。

---

## §1. 场景索引（按业务流反查）

按用户行为 / 业务事件定位 traceId 起点，然后顺 traceId 跨服务查全链。

### 1.1 登录 / Token 刷新

| 关心问题 | 起查日志 fingerprint | 关键字段 |
| --- | --- | --- |
| 用户登录失败原因 | `identity.http.login.received` + 之后 `identity.auth.login.failed` 或 `identity.auth.tokens.issued` | userId, ip, errorCode |
| Token 刷新链路 | `identity.http.refresh.received` → `identity.auth.tokens.issued` | userId, accessJti, refreshJti |
| 注册后地址预分配 | wallet `wallet.address.provision.completed` | userId, addresses |

### 1.2 下单 / 平仓 / 持仓监控

| 关心问题 | 起查日志 fingerprint | 关键字段 |
| --- | --- | --- |
| 市价单成交链路 | trading `trading.order.placed` → `trading.position.opened` → `trading.account.balance.adjusted` | orderId, positionId, userId |
| 手动平仓 | trading `trading.position.close.received` → `trading.position.closed` | positionId, side, pnl |
| 自动强平 | trading `trading.risk.liquidate.triggered` → `trading.position.liquidated` | positionId, reason, liqPrice |
| TP/SL 触发 | trading `trading.pending-order.trigger.fired` → `trading.position.closed` reason=TP_HIT/SL_HIT | triggerId, positionId |
| 风控开关变更 | trading `trading.risk.switch.changed` | switchKey, value, adminUserId |
| 风控动作激活 | trading `trading.risk.action.activated` | actionCode, scope, source |

### 1.3 入金 / 出金 / 对账

| 关心问题 | 起查日志 fingerprint | 关键字段 |
| --- | --- | --- |
| 链上入金检测 | wallet `wallet.deposit.detected` → `wallet.deposit.confirming` → `wallet.deposit.confirmed` | chain, txHash, walletTxId |
| 入金 reverse | wallet `wallet.deposit.reverse.detected` + trading `trading.deposit.reversed` | walletTxId, depositId |
| 出金链上广播 | trading `trading.withdraw.approved` → wallet `wallet.withdraw.broadcast` → `wallet.withdraw.confirmed` | withdrawId, txHash |
| 出金审核失败 | console `admin.http.withdraw.reject.received` → trading 30049/30050 → console 90501/90502 | withdrawId, reason |
| 入金对账异常 | console `admin.http.reconciliation.list.received` → service 内 diff 完整看 unmatched 项 | walletTxId, discrepancyType |
| 手动标记 resolved | console `admin.http.reconciliation.mark-resolved.received` + `admin.reconciliation.mark-resolved` | walletTxId, resolutionType, adminUserId |

### 1.4 KYC / 通知 / 价格告警

| 关心问题 | 起查日志 fingerprint | 关键字段 |
| --- | --- | --- |
| KYC 审核 | console `admin.http.kyc.approve.received` → identity `identity.kyc.review.completed` → trading `trading.notification.created` | submissionId, userId, kycLevel |
| 价格告警触发 | trading `trading.price-alert.triggered` → `trading.notification.created` | alertId, symbol, triggerPrice |
| 站内信发送 | trading `trading.notification.send.received` → `trading.notification.send.completed` | userId, templateCode, notificationId |
| 通知模板 CRUD | console `admin.http.notification-template.*` → trading `trading.notification-template.*` | templateCode, adminUserId |

## §2. 关键日志 fingerprint 一览

按 logger 命名规则：`{service}.{layer}.{action}.{state}`，例如：

- `identity.http.login.received`：identity HTTP 层 login endpoint 收到请求
- `wallet.deposit.confirmed`：wallet 业务层入金确认
- `admin.http.audit-log.list.received`：console-service HTTP 层审计日志列表接收
- `trading.risk.liquidate.triggered`：trading-core 风控层强平触发

完整 logger 命名规范见 [`日志打印规范 §2`](../architecture/日志打印规范.md)；本节仅列 SRE 高频反查场景。

### 2.1 ERROR 级日志（必查）

```
{service}.{module}.failure   # 业务失败（已分类，含 errorCode）
{service}.{module}.exception # 未捕获异常
admin.exception.business     # console 业务异常（含错误码）
admin.exception.internal     # console 未捕获异常
admin.internal-rpc.*.failure # 跨服务调用失败（含 downstream code）
admin.audit.write.failure    # 审计日志写入失败（不阻塞主流程但需告警）
```

### 2.2 WARN 级日志（异常但已处理）

```
admin.exception.business               # 已知业务错误（90xxx 系列）
{service}.repository.cas.conflict      # 数据库 CAS 冲突（重试即可）
wallet.deposit.detected.duplicate      # 重复链上事件（幂等命中）
trading.kafka.consumer.retry.scheduled # Kafka 消费失败重试
```

## §3. traceId 全链联调

### 3.1 MDC traceId 注入点

- **入站**：gateway `TraceIdServletFilter` / 各服务 `TraceIdServletFilter` 把请求 header `X-Trace-Id` 写入 MDC（若 header 缺则生成新 UUID）
- **出站**：`InternalRpcClient.get/post` 把 MDC.traceId 注入下游请求 header（console → wallet / trading-core）
- **Kafka**：`KafkaEventMessageSupport` 把 traceId 写入 record headers；consumer 端 `TraceIdConsumerInterceptor` 读出注入 MDC

所有 logger 输出格式包含 `[traceId={...}]`（详见 logback-spring.xml 各服务）。

### 3.2 跨服务联调模板

**已知 traceId** `abc12345-...`：

```bash
# 本地 docker-compose
docker-compose logs gateway identity-service trading-core-service wallet-service console-service \
  | grep "traceId=abc12345"

# 本地 native（service 单独 java -jar）
grep -rn "traceId=abc12345" /var/log/falconx/*.log

# k8s
for ns_pod in $(kubectl get pods -n falconx -o name); do
  kubectl logs -n falconx $ns_pod --since=1h 2>/dev/null | grep "traceId=abc12345"
done
```

**未知 traceId，已知 userId**（先反查 traceId）：

```bash
grep "userId=$USER_ID" /var/log/falconx/identity-service.log | tail -5 | grep -oE "traceId=[a-f0-9-]+" | sort -u
```

然后用 traceId 走 §3.2 跨服务联调。

## §4. 错误码反查

错误码段位（具体定义见各服务 errorCode java）：

| 段位 | 服务 | 范围 |
| --- | --- | --- |
| `10xxx` | identity | 10001-10099 |
| `20xxx` | wallet | 20001-20099 |
| `30xxx` | trading-core | 30001-30099 |
| `40xxx` | market | 40001-40099 |
| `90xxx` | console（admin 翻译层）| 90000-90999 |
| `99xxx` | 通用框架（Validation / Auth / 5xx 兜底）| 99001-99099 |

### 4.1 console 高频错误码 → 业务流定位

| 错误码 | 含义 | 反查起点 |
| --- | --- | --- |
| `90003` | ADMIN_TOKEN_INVALID | console `admin.auth.token.invalid` |
| `90500-90505` | ADMIN_WITHDRAW_* | console `admin.http.withdraw.*` |
| `90860-90862` | ADMIN_WALLET_PROVISION_* | console `admin.http.wallet.provision-dlq.*` |
| `90880-90887` | ADMIN_NOTIFICATION_* | console `admin.http.notification*` |
| `90900` | ADMIN_AUDIT_LOG_NOT_FOUND | console `admin.http.audit-log.detail.received` |
| `90920-90924` | ADMIN_RECONCILIATION_* | console `admin.http.reconciliation.*` |

### 4.2 跨服务错误码透传

console-service 翻译下游错误码（admin.internal-rpc.*.failure）：

```
30047 trading withdraw not found  →  90500 ADMIN_WITHDRAW_NOT_FOUND
30049 trading withdraw not pending →  90501 ADMIN_WITHDRAW_NOT_PENDING
30050 trading emergency-cancel    →  90502 ADMIN_WITHDRAW_EMERGENCY_CANCEL_NOT_ALLOWED
30060/30065 notification template →  90880 ADMIN_NOTIFICATION_TEMPLATE_NOT_FOUND
20021/20022 wallet provision      →  90861 ADMIN_WALLET_PROVISION_RETRY_NOT_ALLOWED
（transport-level fail）           →  90920/90921 reconciliation unreachable
```

查 console `admin.internal-rpc.*.failure` 行可看 `downstreamCode` 字段。

## §5. 常用 grep / kubectl 模板

### 5.1 docker-compose（本地）

```bash
# 实时 follow 所有服务
docker-compose logs -f gateway identity-service trading-core-service wallet-service console-service market-service

# 按 service + 时间窗
docker-compose logs --since=10m wallet-service | grep ERROR

# 按 traceId 全链
docker-compose logs --since=1h | grep "traceId=abc12345"

# 找最近 5 分钟所有 WARN 以上
docker-compose logs --since=5m 2>&1 | grep -E "WARN|ERROR"

# 计错误码出现频次
docker-compose logs --since=1h console-service | grep -oE "code=[0-9]{5}" | sort | uniq -c | sort -nr
```

### 5.2 k8s pods

```bash
# 单 pod follow
kubectl logs -f -n falconx <pod-name> --tail=200

# 多 pod 聚合（同 deployment）
kubectl logs -f -n falconx -l app=trading-core-service --tail=200

# 按时间窗
kubectl logs -n falconx <pod> --since=10m | grep ERROR

# 跨 service 找 traceId（脚本）
for app in identity-service trading-core-service wallet-service console-service; do
  echo "=== $app ==="
  kubectl logs -n falconx -l app=$app --since=1h --tail=10000 2>/dev/null | grep "traceId=abc12345"
done
```

### 5.3 systemd-journal（生产 native）

```bash
# 单服务实时
journalctl -fu falconx-trading-core-service.service --since="10 min ago"

# 按 traceId
journalctl --since=today -u falconx-* | grep "traceId=abc12345"

# 按 errorCode
journalctl --since="1 hour ago" -u falconx-console-service | grep "code=90500"
```

## §6. 健康检查 / canary 配合查日志

### 6.1 Actuator 健康状态对照

各服务暴露 `/actuator/health`（详见 [`管理端接口规范 §14.5`](../api/管理端接口规范.md)），SRE 应先查 health 再深入日志：

```bash
# 6 服务并发健康检查
for url in http://localhost:18080 http://localhost:18081 http://localhost:18082 \
           http://localhost:18083 http://localhost:18084 http://localhost:18085; do
  echo -n "$url: "
  curl -s $url/actuator/health | python3 -c 'import sys,json; print(json.load(sys.stdin)["status"])'
done

# 等价于 canary health-all（详见 §6.2）
```

### 6.2 canary CLI 触发后查日志

`falconx-canary health-all` / `recon` / `login` 等命令的失败排查：

```bash
# 1. 跑 canary（详见 STAGE-11-OBS-RECON-design.md §3）
java -jar falconx-canary.jar health-all > /tmp/canary-health.json

# 2. canary 报告 JSON 含 baseUrl + httpStatus + error；定位失败 service
cat /tmp/canary-health.json | python3 -m json.tool

# 3. 反查对应 service 同时段日志
docker-compose logs --since=2m <failing-service> | grep -E "WARN|ERROR"
```

## §7. 入金对账故障排查（STAGE-11 §11.4 特有）

### 7.1 unmatched 项 ≥ 阈值（canary recon 报 FAIL）

```bash
# 1. 查 console 端 list 调用日志
docker-compose logs --since=10m console-service | grep "admin.http.reconciliation.list"

# 2. 查 console → wallet/trading-core internal RPC 是否 timeout
docker-compose logs --since=10m console-service | grep -E "internal-rpc.*reconciliation"

# 3. 查 wallet 端 confirmed 入金是否堆积（未推进到 trading-core 入账）
docker-compose logs --since=1h wallet-service | grep "wallet.deposit.confirmed" | wc -l
docker-compose logs --since=1h trading-core-service | grep "trading.deposit.credit.completed" | wc -l
# 两数差值 ≈ unmatched WALLET_ONLY 项数
```

### 7.2 mark-resolved 失败

```bash
# 90924 已被另一 admin 标记
docker-compose logs --since=10m console-service | grep "code=90924"

# 90923 reason 缺失/过短（前端漏校验）
docker-compose logs --since=10m console-service | grep "code=90923"

# 90920/90921 后端不可达
docker-compose logs --since=10m console-service | grep -E "code=(90920|90921)"
```

### 7.3 已 resolved 项审计追溯

```bash
# 通过审计日志页 (P18) 反查：
#   permissionCode=reconciliation:resolve
#   targetType=reconciliation
#   targetId={walletTxId}
# 或直接查 console 日志
docker-compose logs --since=24h console-service | grep "admin.reconciliation.mark-resolved walletTxId=880000001"
```

## §8. 已知局限

1. **不预设外部日志平台**：本手册仅给 grep / kubectl / journalctl 模板。生产环境接入 Elasticsearch / Splunk / Loki 后，由运维补对应平台的查询语法（Kibana KQL / Splunk SPL / LogQL），不在 V2 一期范围内。
2. **traceId 跨 Kafka 链路**：consumer 端从 record headers 读 traceId 注入 MDC，但若 producer 没正确写 headers（V2 一期部分老链路漏，详见 [`Kafka事件规范`](../event/Kafka事件规范.md)），traceId 会断链；这些点归 R6 二轮统一治理。
3. **canary 日志**：`falconx-canary` 自身只在 stdout 输出 JSON 报告，不写 logback 文件；如需归档，cron 调用方应 `>> /var/log/falconx-canary.log` 自行收集。
4. **审计日志 vs 业务日志**：`t_admin_operation_log` 表是结构化审计数据（详见 P18 审计日志页），与 logback 文件日志互补。SRE 查"谁做了什么"优先用 P18；查"为什么失败"用本手册。
