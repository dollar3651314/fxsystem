# 管理端接口规范（V1，2026-05-08）

> 本文件冻结 falconx-console-service 对外 REST 接口契约。客户端 API 仍以 [`REST 接口规范`](./REST接口规范.md) 与 [`FalconX 统一接口文档`](./FalconX统一接口文档.md) 为真源。
>
> 阶段 1 仅冻结 auth + me + permissions 最小集；后续阶段（客户/出金/KYC/...）的管理端 API 在对应阶段启动时增量补充到本文件。

---

## §1. 通用约定

### 1.1 路径前缀

所有管理端 API 统一以 `/admin/*` 开头，由 gateway 路由到 falconx-console-service:18085（按用户决策 D2，复用 C 端域名）。

### 1.2 认证

- **登录态**：`Authorization: Bearer {admin_jwt_access_token}`
- **管理端 JWT 与 C 端 JWT 完全独立**：
  - 不同的 RSA 私钥（FalconX_CONSOLE_PRIVATE_KEY_PEM 配置）
  - 不同的 issuer（`falconx-console-service`）
  - 不同的过期时间（access 30m，refresh 8h，比 C 端短）
  - C 端 JWT 在管理端无效；反之亦然
- **JWT payload**：`sub`(adminUserId) / `username` / `roles[]` / `iat` / `exp` / `jti` / `mustChangePassword`

### 1.3 IP 白名单

- gateway 路由级：`/admin/**` 通过 `falconx.gateway.security.admin-ip-whitelist`（阶段 1 实施时由 R2 落地）
- console-service 应用级：再次校验 IP（gateway 配置错误时的兜底，由 R9 实施）
- dev profile 下默认禁用（`falconx.console.security.ip-whitelist-enabled=false`）

### 1.4 统一响应结构

复用 [`falconx-common.ApiResponse`](../../falconx-common/src/main/java/com/falconx/common/api/ApiResponse.java)：

```json
{
  "code": "0",
  "message": "success",
  "data": { ... },
  "timestamp": "2026-05-08T12:34:56.789Z",
  "traceId": "abc123..."
}
```

### 1.5 错误码空间

**管理端独占 `90001-90899` 号段**（用户决策于 2026-05-08；与客户端 `1xxxx`-`5xxxx` 完全隔离；后续新增管理端错误码必须在 `90001-90899` 内向上分配，禁止复用 C 端号段）。

**`99xxx` 高位为系统级跨服务通用错误码**（FX-069 决策于 2026-05-09，由 `falconx-common.CommonErrorCode` 维护：99001 INTERNAL_ERROR / 99002 DEPENDENCY_TIMEOUT / 99003 EVENT_PUBLISH_FAILED / 99004 INVALID_REQUEST_PAYLOAD），不在管理端独占段内，与 C 端、Admin 端业务段全部隔离。

### 3.3 冻结客户

| 字段 | 内容 |
| --- | --- |
| 路径 | `POST /admin/customers/{userId}/freeze` |
| 认证 | Bearer Admin JWT |
| 权限 | `customer:freeze`（高风险） |
| 请求体 | `{ "reason": "..." }`（必填，长度 ≥ 10） |

业务逻辑：

1. console 校验 reason 长度 ≥ 10（错误码 `90304` `ADMIN_REASON_TOO_SHORT`）
2. console 通过 `POST /internal/v1/identity/users/{userId}/freeze` 调用 identity（gateway 注入 `X-Internal-Token`）
3. identity 校验状态机：当前 `ACTIVE` → `FROZEN`；当前已 `FROZEN` 返回 `90305` `ADMIN_CUSTOMER_ALREADY_FROZEN`；当前 `BANNED` 拒绝（`90306` `ADMIN_CUSTOMER_TERMINAL_STATUS`）
4. console 写 `t_admin_operation_log`（risk_level=HIGH_RISK，before/after JSON）

成功响应：

```json
{ "code": "0", "data": { "userId": 100023, "previousStatus": "ACTIVE", "newStatus": "FROZEN" } }
```

### 3.4 解冻客户

| 字段 | 内容 |
| --- | --- |
| 路径 | `POST /admin/customers/{userId}/unfreeze` |
| 认证 | Bearer Admin JWT |
| 权限 | `customer:unfreeze`（高风险） |
| 请求体 | `{ "reason": "..." }`（必填，长度 ≥ 10） |

业务逻辑同 §3.3，状态迁移 `FROZEN → ACTIVE`。token 不主动恢复（用户必须重新登录获取新 token）。

### 3.5 调余额

| 字段 | 内容 |
| --- | --- |
| 路径 | `POST /admin/customers/{userId}/balance/adjust` |
| 认证 | Bearer Admin JWT |
| 权限 | `customer:balance:adjust`（高风险） |
| 请求体 | `{ "deltaUSD": "100.00", "reason": "..." }`（reason 长度 ≥ 10；deltaUSD 可正可负，精度 2 位小数） |

业务逻辑：

1. console 校验：`abs(deltaUSD) ≤ 5000`（否则 `90301`）
2. console 检查 Redis 当日累计（按 [`管理端架构`](../architecture/管理端架构.md) §4.4）：当日累计 + `abs(deltaUSD)` ≤ 20000（否则 `90302`）；Redis 计数不可用时 fail-closed，返回系统内部错误，不继续调用 trading-core
3. console 通过 `POST /internal/v1/trading/accounts/{userId}/balance/adjust` 调用 trading-core（直接调 trading-core，**不经过 identity**——余额 owner 是 trading-core）
4. trading-core 写 `t_account.balance` + `t_ledger`（biz_type=ADMIN_BALANCE_ADJUST，memo=reason，ref_id=traceId）
5. console Redis `INCRBY abs(deltaUSD)` 成功后调用 trading-core；接口成功返回后写 `t_admin_operation_log`（risk_level=HIGH_RISK，before/after JSON 含 deltaUSD/balanceBefore/balanceAfter）

成功响应：

```json
{
  "code": "0",
  "data": {
    "userId": 100023,
    "deltaUSD": "100.00",
    "balanceBefore": "1234.56",
    "balanceAfter": "1334.56",
    "ledgerEntryId": "ledger-..."
  }
}
```

### 3.6 阶段 2.1 错误码块（90300-90399）

| 错误码 | 含义 | HTTP |
| --- | --- | --- |
| `90301` | ADMIN_BALANCE_ADJUST_SINGLE_LIMIT_EXCEEDED 单次调余额超 $5000 | 400 |
| `90302` | ADMIN_BALANCE_ADJUST_DAILY_LIMIT_EXCEEDED 单日累计超 $20000 | 400 |
| `90303` | ADMIN_CUSTOMER_NOT_FOUND 客户不存在 | 404 |
| `90304` | ADMIN_REASON_TOO_SHORT 操作原因 < 10 字符 | 400 |
| `90305` | ADMIN_CUSTOMER_ALREADY_FROZEN 客户已冻结 | 409 |
| `90306` | ADMIN_CUSTOMER_TERMINAL_STATUS 客户处于终态（BANNED）不可操作 | 409 |
| `90307` | ADMIN_BALANCE_INSUFFICIENT_FOR_NEGATIVE_ADJUST 扣减后余额为负 | 400 |

## §4. 跨服务 internal RPC 契约（被 console-service 调用）

internal RPC 鉴权见 [`管理端架构`](../architecture/管理端架构.md) §4.1：所有 `/internal/v1/**` 必须包含 `X-Internal-Token` + `X-Admin-User-Id` + `X-Trace-Id`；缺失 / 无效返回 `90701/90702`。

### 4.1 identity-service: 冻结用户

| 字段 | 内容 |
| --- | --- |
| 路径 | `POST /internal/v1/identity/users/{userId}/freeze` |
| owner | identity-service |
| 调用方 | console-service |
| 请求体 | `{ "reason": "..." }` |

返回：`{ "userId": 100023, "previousStatus": "ACTIVE", "newStatus": "FROZEN" }`

错误码（identity 业务码段 1xxxx）：

- `10012` `IDENTITY_USER_NOT_FOUND`（404）
- `10013` `IDENTITY_USER_ALREADY_FROZEN`（409）
- `10014` `IDENTITY_USER_TERMINAL_STATUS`（409，已 BANNED）

业务行为：

- `t_user.status` `ACTIVE → FROZEN`（按 [`状态机规范`](../domain/状态机规范.md) §2 已冻结迁移规则）
- 该用户所有 access token jti 加入 Redis 黑名单（同改密链路）
- 该用户所有 refresh token 撤销

### 4.2 identity-service: 解冻用户

| 字段 | 内容 |
| --- | --- |
| 路径 | `POST /internal/v1/identity/users/{userId}/unfreeze` |
| 请求体 | `{ "reason": "..." }` |

业务行为：`FROZEN → ACTIVE`。token 不主动恢复（用户必须重新登录）。

### 4.3 trading-core-service: 调整账户余额

| 字段 | 内容 |
| --- | --- |
| 路径 | `POST /internal/v1/trading/accounts/{userId}/balance/adjust` |
| owner | trading-core-service |
| 调用方 | console-service |
| 请求体 | `{ "deltaUSD": "100.00", "reason": "..." }` |

业务行为：

- 在 `t_account` UPDATE balance（FOR UPDATE 行锁）
- 写 `t_ledger`（`biz_type=ADMIN_BALANCE_ADJUST`，`ref_id=<console traceId>`，`memo=<reason>`）
- 同事务

错误码（trading 业务码段 3xxxx）：

- `30030` `TRADING_ACCOUNT_NOT_FOUND`（404）
- `30031` `TRADING_BALANCE_INSUFFICIENT`（409，余额不足以扣减）

返回：`{ "userId": 100023, "deltaUSD": "100.00", "balanceBefore": "1234.56", "balanceAfter": "1334.56", "ledgerEntryId": "..." }`

### 4.3a trading-core-service: 平台风控配置（STAGE-14D3a，D3b console 透传目标）

> STAGE-14D3a（trading-core 后端）落地 internal RPC 写/读冷静期 + StopOut/MarginCall 阈值 + FX_PAUSED 8 类目行为开关；**D3b console 透传到这些 trading-core 端点**（console 三端 UI 未做）。鉴权同 §4：`X-Internal-Token` + `X-Admin-User-Id` + `X-Trace-Id`。详见 [统一接口文档 §3.32](FalconX统一接口文档.md)。

| 路径 | owner | 调用方 | 校验 / 行为 |
| --- | --- | --- | --- |
| `GET /internal/v1/trading/console/config/platform-risk` | trading-core | console（D3b） | 读冷静期 + 阈值 |
| `PUT /internal/v1/trading/console/config/cooling-period` | trading-core | console（D3b） | `coolingPeriodSeconds` 60-604800；越界 → 99004 |
| `PUT /internal/v1/trading/console/config/risk-thresholds` | trading-core | console（D3b） | stopOut 0.05-0.95 / marginCall 0.50-2.00；越界 → 99004 |
| `GET /internal/v1/trading/console/config/fx-pause-behavior` | trading-core | console（D3b） | 读全量 8 行 |
| `PUT /internal/v1/trading/console/config/fx-pause-behavior/{category}` | trading-core | console（D3b） | category 1-8 + 三开关 `@NotNull`；`X-Admin-User-Id` 落审计列；`allow_close` 恒 1 |

> **owner 修正（master §7.4 设计稿偏差）**：master §7.4 把 fx pause behavior admin 路由写成 `/admin/market/fx/pause-behavior`（market）；实际 `t_fx_pause_behavior` 表**物理在 trading-core `falconx_trading` 库**，故 **fx-pause-behavior 透传目标修正为 trading-core**（market 不得写 trading 库，[`架构边界`](../../AGENTS.md) §3.2）。

**D3b console 端点（前端 → console-service，✅ 已实现，详见 §19）：**

| console 端点 | 透传目标 | RBAC（view/edit，edit 高危） |
| --- | --- | --- |
| `GET\|PUT /admin/trading/margin-mode-config` | trading `GET .../config/platform-risk` + `PUT .../config/cooling-period` | `margin-mode-config:view\|edit` |

### 5.1 管理员管理（admin-users）

#### 5.1.1 列表查询

`GET /admin/admin-users` — 权限 `admin-user:view`

查询参数：`username` (模糊) / `realName` (模糊) / `status` (`ACTIVE` | `DISABLED`) / `roleCode` / `from` / `to` / `page` (默认 0) / `size` (默认 20，最大 100)

响应 `data`：

```json
{
  "items": [
    {
      "id": 100023,
      "username": "alice",

      "roles": [{ "code": "FINANCE", "name": "财务" }],

      "createdAt": "2026-04-01T08:00:00Z"
    }

  "total": 42,
  "page": 0,
  "size": 20
}
```

#### 5.1.2 详情

`GET /admin/admin-users/{id}` — 权限 `admin-user:view`，返回字段同 5.1.1 单项。错误码 `90211` `ADMIN_USER_NOT_FOUND`（404）。

#### 5.1.3 新建

`POST /admin/admin-users` — 权限 `admin-user:create`

请求体：

```json
{
  "username": "alice",
  "realName": "张三",
  "roleIds": [2, 3],
  "password": null,
  "mustChangePassword": true
}
```

约束：

- `username` 3-32 字符 `[a-zA-Z0-9_]+`，UNIQUE
- `roleIds` 不允许包含 SUPER_ADMIN role_id (=1)
- `password` 可空：缺省时后端自动生成 16 位随机密码
- `mustChangePassword` 默认 `true`，首次登录强制改密

响应 `data`：

```json
{
  "id": 100024,
  "username": "alice",
  "generatedPassword": "K8x@mP9!nQwT2vR$"
}
```

> `generatedPassword` 仅当请求体 `password=null` 时返回；客户端必须立即记录并通知用户，本次响应后不再可查。

错误码：

- `90210` `ADMIN_USER_USERNAME_DUPLICATE`（409）
- `90212` `ADMIN_USER_USERNAME_INVALID_FORMAT`（400）
- `90213` `ADMIN_USER_SUPER_ADMIN_ROLE_NOT_ASSIGNABLE`（400）
- `90100` `ADMIN_PASSWORD_POLICY_VIOLATION`（400，复用 R9.5 段）

#### 5.1.4 编辑

`PUT /admin/admin-users/{id}` — 权限 `admin-user:update`

请求体：`{ "realName": "...", "roleIds": [2, 3] }`（不允许改 username；status 通过 disable/enable 接口修改）

约束：

- 不允许从 SUPER_ADMIN 用户的 roles 中移除 SUPER_ADMIN 角色（错误码 `90214` `ADMIN_USER_SUPER_ADMIN_ROLE_LOCKED`）

#### 5.1.5 启用 / 禁用

`POST /admin/admin-users/{id}/disable` — 权限 `admin-user:disable`，请求体 `{ "reason": "..." }`（reason ≥ 10）

`POST /admin/admin-users/{id}/enable` — 权限 `admin-user:disable`（共用），请求体 `{}`

约束：

- 禁止禁用自己（`90215` `ADMIN_USER_CANNOT_DISABLE_SELF`）
- 禁用立即生效：该用户所有 access token jti 加入 Redis 黑名单 + refresh token 全部撤销
- 高风险 + 审计 risk_level=HIGH_RISK

#### 5.1.6 重置密码

`POST /admin/admin-users/{id}/reset-password` — 权限 `admin-user:reset-password`（高风险）

请求体：

```json
{
  "password": null,
  "forceChangePassword": true,
  "reason": "..."
}
```

响应：`{ "id": 100024, "generatedPassword": "..." }`（仅当 password=null 时返回）

副作用：该用户所有现有 access/refresh token 立即失效。

#### 5.1.7 删除

`DELETE /admin/admin-users/{id}` — 权限 `admin-user:delete`（高风险）

Header：`X-Operation-Reason` 必填（长度 ≥ 10）

约束：

- 禁止删除 SUPER_ADMIN 角色用户（`90216` `ADMIN_USER_SUPER_ADMIN_NOT_DELETABLE`）
- 禁止删除自己（`90217` `ADMIN_USER_CANNOT_DELETE_SELF`）
- 物理删除 `t_admin_user` 行；`t_admin_operation_log` 历史审计保留

- `90220` `ADMIN_ROLE_CODE_DUPLICATE`（409）

- `90222` `ADMIN_ROLE_IS_SYSTEM_NOT_EDITABLE`（403）

#### 6.13.5 trading-core SymbolSpec 消费

market 在 mapping CRUD `afterCommit` 把 `SymbolSpec`（含 leverage/fee/spread/qty/precision）写入 Redis Hash `falconx:market:symbol-spec:{platformSymbol}`；trading-core 启动 warmup + 本地 10s 缓存。开仓校验时：

- effective max leverage = `min(mapping.max_leverage, t_risk_config.max_leverage)`
- fee_rate 取 `mapping.taker_fee_rate`，开仓时快照入 `t_order.open_fee_rate / t_position.open_fee_rate`
- qty / notional 校验取 `mapping.min_qty / max_qty / min_notional`
- 拒单错误码新增（trading 业务段）：`SYMBOL_SPEC_NOT_FOUND / QTY_BELOW_MIN / QTY_ABOVE_MAX / NOTIONAL_BELOW_MIN`

详见 [`管理端架构`](../architecture/管理端架构.md) §4.3 跨 schema 只读查询规则 + [任务卡 §C](../process/task-cards/STAGE-2-SYMBOL-PARAMS-DOWNSHIFT.md)。

#### 6.13.6 强制约束

- Phase A（schema + 管理端可配）与 Phase B（trading-core 消费）**必须捆绑发布**，任何分阶段部署都视为违反任务卡。如果只部署 Phase A，trading-core 仍用 `defaultFeeRate / properties.maxLeverage`，**管理端调 mapping 的 leverage/fee 不会生效**，是不可接受的中间状态
- Flyway 编号：market `V11` + console `V2` + trading `V13`
- 历史 `t_order / t_position` 通过 `open_fee_rate` 快照保护，运营改 mapping 不影响存量持仓的费率口径

### 6.14 用户组加点管理（t_symbol_group_markup，STAGE-12-GROUP-MARKUP）

> 任务卡：`STAGE-12-GROUP-MARKUP`。本节冻结契约，R4/R9/R10 按此实施。
> 配套设计稿：[STAGE-12-GROUP-MARKUP-design](../design/STAGE-12-GROUP-MARKUP-design.md)。

在已有「平台对 LP 统一加点」（`t_symbol_quote_mapping.bid_adjustment / ask_adjustment`）之上，叠加一层「用户组级 bid/ask 双向加点」。两层加点的最终效果：

```
平台 Layer 1 价：bid = LP.bid × multiplier + bid_adjustment
                ask = LP.ask × multiplier + ask_adjustment
用户组 Layer 2 价：bid = Layer1.bid + bid_extra
                  ask = Layer1.ask + ask_extra
```

Layer 2 加点仅影响：客户端 REST / WS 推送 / 撮合 fillPrice / 平仓 exitPrice / 持仓未实现 PnL / 强平触发 / 挂单触发。**不影响**：K 线 OHLC / ClickHouse `quote_tick` 落盘 / Kafka `falconx.market.price.tick` / 管理员视角看板。

```
│       ▼                                                               │
│  ┌─────────────────────────────────┬─────────────────────────────┐   │
│  │ t_symbol_group_visibility       │ t_symbol_group_markup       │   │
│  │ PK: (group_code, symbol)        │ PK: (group_code, platform   │   │
│  │ 字段: visible (0/1)             │      _symbol)               │   │
│  │                                 │ 字段: bid_extra, ask_extra, │   │
│  │                                 │      enabled (0/1)          │   │
│  ├─────────────────────────────────┼─────────────────────────────┤   │
│  │ 职责: 该组能否 "看见 / 订阅 /    │ 职责: 该组对该 symbol 报价  │   │
│  │      查询" 该 symbol            │      加多少 bid/ask 加点    │   │
│  │ 缺记录或 visible=0 → 用户       │ 缺记录或 enabled=0 → 自动   │   │
│  │      查询报 30001 not-found     │      回退基准价（零异常）   │   │
│  │ 配置入口: §6.13                  │ 配置入口: §6.14 (本节)       │   │
│  └─────────────────────────────────┴─────────────────────────────┘   │
│                                                                       │
│  生效路径（market-service / trading-core）：                          │
│   ① visibility:   MarketSymbolRepository.findVisibleTradingSymbol    │
│                    (symbol, groupCode)                                │
│   ② markup 应用:  MarketGroupMarkupService.applyMarkup(quote, group) │
│   ③ 撮合 fillPrice: 开仓时按 group_code 查 markup + position 冻结    │
│                    (groupCodeAtOpen, bidExtraAtOpen, askExtraAtOpen) │
└──────────────────────────────────────────────────────────────────────┘
```

**两表完全解耦** — visibility 与 markup 不会互相校验，配错任一边只影响该单一职责：

| 场景 | visibility | markup | 用户体验 |
| --- | --- | --- | --- |
| 既可见又有加点 | `visible=1` | 有非零配置 | 看到 markup 后的价 |
| 可见但无 markup 配置 | `visible=1` | 缺记录 | 看到基准价（applyMarkup 零分配回退） |
| 可见但 markup 停用 | `visible=1` | `enabled=0` | 看到基准价（同上） |
| 不可见但配了 markup | `visible=0` 或缺 | 有配置 | 查询 30001 not-found，markup 配置形同虚设 |
| 既不可见也无 markup | 缺 | 缺 | 查询 30001 not-found |

**运营动作矩阵**：

| 想做 | 操作的表 | 入口章节 | 备注 |
| --- | --- | --- | --- |
| 把用户分到某组 | `t_user.group_code` | identity 后端（不在管理端 R9） | 仅 identity-service 暴露管理 API |
| 让某组看到某 symbol | `t_symbol_group_visibility` | §6.13 | 共用 group_code，新组首次配置必走 |
| 让某组对某 symbol 加点 | `t_symbol_group_markup` | §6.14（本节） | 与 visibility 完全独立 |
| 给新组完整开通 | 上面两张表都要配 | §6.13 + §6.14 | 缺 visibility 时 markup 配了也用不到 |
| 改某用户分组 | 改 `t_user.group_code` 即可 | identity | 两张配置表立即生效（≤ 30s 内存快照刷新） |

**典型新建组流程**（例：开通 `vip` 让利组）：

```
① identity 后端把目标用户的 t_user.group_code 改为 'vip'
② 管理端 §6.13 给 vip 组配 visibility（哪些 symbol 让 vip 看见）
③ 管理端 §6.14 给 vip 组配 markup（看见的 symbol 让利/加价多少）
④ ≤ 30s 后 market-service / trading-core 内存快照全部刷新生效
```

### 11.6 已知技术债（R2 二轮记录，归 P2 enhancement）

阶段 5 commit `f91fcd6` + `db75a91` 落地时早于 STAGE-6-KYC contract + headers 标准化，存在以下与后续阶段不一致的实现细节：

1. **identity 未使用 `IdentityUserRegisteredEventPayload` contract record**：当前 `IdentityKafkaEventPublisher.publishUserRegistered` 直接 `LinkedHashMap → JSON`；wallet 端 consumer 用 `JsonNode` 解析。与 STAGE-6-KYC `KycReviewedEventPayload`、STAGE-7-WITHDRAW `WalletWithdraw*EventPayload` 的 contract 模块化标准不一致。
2. **identity 未使用 `KafkaEventMessageSupport` headers**：缺 `X-Event-Id` / `X-Event-Type` / `X-Event-Source` / `X-Trace-Id` Kafka headers。Kafka 事件规范 §12.13 列出运行时期望 headers，但当前生产端为兼容历史只写 payload body 内的 `eventId`/`eventType`。
3. **identity 未使用 Outbox 模式**：注册事务 afterCommit 直接调用 Kafka publisher，Kafka 抖动会丢事件；当前由 wallet DLQ + 后台运营手动重试兜底。是否切 Outbox 视后续 Kafka 可用性观测决定。

这三项不阻塞阶段 5 收口（DLQ 兜底机制完整），后续如需统一化在新一轮专项中处理。

`resolutionType` 枚举：

| 枚举 | 语义 |
| --- | --- |

- 写 `t_admin_operation_log`（`permission_code='reconciliation:resolve'`、`target_type='reconciliation'`、`target_id={walletTxId}`、`before_value={discrepancyType,...}`、`after_value={resolutionType,reason}`、`risk_level='HIGH_RISK'` — OperationAuditAspect 通过 HighRiskPermissionRegistry 自动判定，§4.A 三端硬约束统一两档语义）

### 14.6 §11.2 canary 自动化脚本（运维任务，无 admin API）

新增 `falconx-canary` Maven module（Spring Boot CLI / picocli 二选一，R4 实施时定），提供 5-7 个关键链路检查命令：

| 命令 | 链路 | 校验点 |
| --- | --- | --- |

| --- | --- |

| RBAC | 无（internal-only） |

```json
{
```

- 不存在：200，`ApiResponse` error `60010 FX_SYMBOL_NOT_CONFIGURED`（"FX symbol 未配置: {BASE}/{QUOTE}"）

### 15.3 Payload 契约（`FxRateSnapshotPayload`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |

## §21. 用户信息 enrich 字段（跨切面，2026-06-04）

为便于运营辨识，所有「用户关联」admin 列表/详情响应在 console 端统一附带用户基本信息（不改既有字段，仅追加）。

- **新增字段（均可空，null = 未 enrich / 用户不存在）**：
  - `userUid`：用户对外短号（`t_user.uid`）
  - `userEmail`：用户邮箱（`t_user.email`）
  - `userFullName`：用户姓名（`t_user_profile.first_name + last_name`，口径同客户管理 `fullName`）
- **覆盖端点（响应 item / 详情对象追加上述字段）**：订单 `/admin/trading/orders`、持仓 `/admin/trading/positions`、价格告警 `/admin/trading/price-alerts`、入金 `/admin/deposits`、出金 `/admin/withdraws`（原已有 `userEmail`，本次补 `userUid`/`userFullName`）、KYC `/admin/kyc`、通知 `/admin/notifications`、用户风控阈值 `/admin/risk/user-thresholds`、入金对账 `/admin/reconciliation/unmatched`。
- **实现**：console 端按 userId 批量跨 schema 查 `falconx_identity.t_user (+ t_user_profile)` 装配（`AdminUserInfoEnricher` + `AdminUserInfoEnrichmentMapper`），复用既有 `falconx_identity` SELECT 权限与出金审核 enrich 范式；best-effort，enrich 失败保留原响应不阻塞。**无新增 identity RPC**。
- **未覆盖（deferred）**：挂单 `/admin/pending-orders`（DTO 本身不含 userId，需 trading-core 先在 RPC 补 userId）；审计日志 `adminUserId` 为管理操作员非普通用户，不在本范围。
